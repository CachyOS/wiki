Το Extensible Scheduler Class (πιο γνωστό ως `sched-ext`) είναι ένα χαρακτηριστικό του πυρήνα Linux που επιτρέπει την υλοποίηση χρονοπρογραμματιστών νημάτων πυρήνα σε
BPF (Berkeley Packet Filter) και τη δυναμική φόρτωσή τους. Ουσιαστικά, αυτό επιτρέπει στους τελικούς χρήστες να αλλάζουν χρονοπρογραμματιστές στον χώρο χρήστη, χωρίς
να χρειάζεται να μεταγλωττίσουν έναν άλλο πυρήνα μόνο και μόνο για να έχουν διαφορετικό χρονοπρογραμματιστή.

:::note
Η χρήση οποιουδήποτε από τους χρονοπρογραμματιστές sched-ext θα αποσυνδέσει προσωρινά τον προεπιλεγμένο χρονοπρογραμματιστή του πυρήνα. Όταν διακοπεί ένας χρονοπρογραμματιστής sched-ext, ο προεπιλεγμένος χρονοπρογραμματιστής του πυρήνα θα αναλάβει ξανά.

Παράδειγμα: EEVDF ή BORE.
:::

:::tip[Επικοινωνήστε με τους προγραμματιστές στον [διακομιστή Discord](https://discord.gg/b2J8DrWa7t) τους]
:::

- *Οι χρονοπρογραμματιστές βρίσκονται στα πακέτα `scx-scheds` και `scx-scheds-git`.*
  ```sh
  # Σταθερός κλάδος + τα εργαλεία scx_loader και scxctl.
  sudo pacman -S scx-scheds scx-tools

  # Κλάδος bleeding edge (Αυτός ο κλάδος περιλαμβάνει τις πιο πρόσφατες αλλαγές από τον κλάδο master.) + τα εργαλεία scx_loader και scxctl.
  sudo pacman -S scx-scheds-git scx-tools-git
  ```

  :::note
  Το πακέτο `scx-scheds-git` ενδέχεται να μην περιλαμβάνει κάθε πειραματικό χρονοπρογραμματιστή, καθώς ορισμένοι αναπτύσσονται σε ξεχωριστούς κλάδους δυνατοτήτων που δεν έχουν ακόμη συγχωνευθεί στον κλάδο master.
  :::

## Εκκίνηση και διαχείριση του χρονοπρογραμματιστή

:::note
Τόσο το `scxctl` όσο και το `scx_loader` απαιτούν δικαιώματα διαχειριστή για την εκκίνηση, τη διακοπή και την εναλλαγή χρονοπρογραμματιστών.

Επομένως, θα πρέπει να τα εκτελέσετε με `sudo` ή χρησιμοποιώντας έναν παράγοντα polkit (polkit agent) που παρέχει τα απαραίτητα δικαιώματα.

Χωρίς `sudo`, τα scxctl/scx_loader θα ζητήσουν έλεγχο ταυτότητας μέσω ενός παράγοντα polkit.
:::

  - Εμφάνιση του τρέχοντος χρονοπρογραμματιστή και της λειτουργίας του

  - Εναλλαγή μεταξύ χρονοπρογραμματιστών και λειτουργιών
  - Διακοπή του εκτελούμενου χρονοπρογραμματιστή
  - Επανεκκίνηση του εκτελούμενου χρονοπρογραμματιστή

*Όπως υποδηλώνει το όνομά του, είναι ένα βοηθητικό πρόγραμμα που λειτουργεί ως φορτωτής (loader) και διαχειριστής για το πλαίσιο sched-ext χρησιμοποιώντας τη διεπαφή D-Bus.*

*Παρόλο που δεν απαιτεί το systemd, μπορεί να χρησιμοποιηθεί σε συνδυασμό με αυτό.* [Δείτε τον οδηγό μετάβασης για αναφορά](/el/configuration/sched-ext#μετάβαση-από-το-scxservice-στο-scx_loader-πλήρης-οδηγός).

- Έχει τη δυνατότητα να διακόπτει, να εκκινεί, να επανεκκινεί, να διαβάζει πληροφορίες σχετικά με έναν χρονοπρογραμματιστή scx και άλλα.
  - *Μπορείτε να χρησιμοποιήσετε εργαλεία όπως τα `dbus-send` ή `gdbus` για να επικοινωνήσετε μαζί του.*
- Αυτός ο οδηγός εξηγεί πώς να χρησιμοποιήσετε το `scx_loader` με την εντολή `dbus-send`.
  - ```sh title='Εκκίνηση του scx_rusty με τα προεπιλεγμένα ορίσματά του'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.StartScheduler string:scx_rusty uint32:0
    ```
  - ```sh title='Εκκίνηση χρονοπρογραμματιστή με ορίσματα'
    # Αυτό το παράδειγμα εκκινεί το scx_bpfland με τις εξής παραμέτρους: -k -c 0
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.StartSchedulerWithArgs string:scx_bpfland array:string:"-k","-c","0"
    ```
  - ```sh title='Διακοπή του τρέχοντος εκτελούμενου χρονοπρογραμματιστή'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.StopScheduler
    ```
  - ```sh title='Εναλλαγή στον προεπιλεγμένο χρονοπρογραμματιστή'
    # Το scx_loader θα μεταβεί στον προεπιλεγμένο χρονοπρογραμματιστή που έχει οριστεί στο αρχείο ρύθμισης του scx_loader
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.RestoreDefault
    ```
  - ```sh title='Εναλλαγή σε άλλον χρονοπρογραμματιστή στη λειτουργία Mode 2'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.SwitchScheduler string:scx_lavd uint32:2
    # Αυτό κάνει εναλλαγή στο scx_lavd με τη λειτουργία χρονοπρογραμματιστή 2, που σημαίνει ότι εκκινεί το LAVD σε εξοικονόμηση ενέργειας
    ```
  - ```sh title='Εναλλαγή σε άλλον χρονοπρογραμματιστή με ορίσματα'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.SwitchSchedulerWithArgs string:scx_bpfland array:string:"-k","-c","0"
    ```
  - ```sh title='Λήψη του τρέχοντος εκτελούμενου χρονοπρογραμματιστή'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.freedesktop.DBus.Properties.Get string:org.scx.Loader string:CurrentScheduler
    ```
  - ```sh title='Λήψη λίστας με τους υποστηριζόμενους χρονοπρογραμματιστές'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.freedesktop.DBus.Properties.Get string:org.scx.Loader string:SupportedSchedulers
    ```
:::tip
Ακολουθεί μια εξήγηση για το τι σημαίνει κάθε λειτουργία (Mode) στο `scx_loader`:

- Mode 0 = `Default scheduler flags` (Προεπιλεγμένες παράμετροι χρονοπρογραμματιστή)
- Mode 1 = `Gaming` (Παιχνίδια)
- Mode 2 = `Power Saving` (Εξοικονόμηση ενέργειας)
- Mode 3 = `Low Latency` (Χαμηλή καθυστέρηση)
- Mode 4 = `Server` (Διακομιστής)

Παράδειγμα: Η εκτέλεση του LAVD στη λειτουργία Mode 1 ισοδυναμεί με το `scx_lavd --performance`

*Συνοπτικά: Κάθε λειτουργία είναι ένα σύνολο διαφορετικών παραμέτρων που αποσκοπούν στη βελτίωση της εκάστοτε περίπτωσης χρήσης.*

[Για μια πιο αναλυτική ματιά στο τι αλλάζουν αυτές οι λειτουργίες σε κάθε χρονοπρογραμματιστή](<https://github.com/sched-ext/scx-loader/blob/main/crates/scx_loader/src/config.rs#L193>)

## Οδηγός χρονοπρογραμματιστών: Προφίλ και περιπτώσεις χρήσης

Επειδή υπάρχουν πολλοί χρονοπρογραμματιστές για να επιλέξετε, θέλουμε να σας δώσουμε μια σύντομη εισαγωγή για τους διαθέσιμους χρονοπρογραμματιστές.

:::note
Αυτοί οι χρονοπρογραμματιστές βρίσκονται υπό συνεχή ανάπτυξη ενώ δοκιμάζονται, οπότε να αναμένετε ότι ορισμένες από τις δυνατότητες ή τις παραμέτρους τους ενδέχεται να αλλάξουν.
:::

Μη διστάσετε να αναφέρετε τυχόν προβλήματα ή σχόλια στο αποθετήριο του αντίστοιχου χρονοπρογραμματιστή.

Χρησιμοποιήστε την εντολή `scx_schedulername --help` για να δείτε τις διαθέσιμες παραμέτρους και μια σύντομη περιγραφή του τι κάνουν.

```sh title='Παράδειγμα λήψης βοήθειας για το scx_rusty'
scx_rusty --help
```

### [scx_beerland](https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_beerland)

**Ανάπτυξη από: Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

Έτοιμο για παραγωγική χρήση; <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

Το scx_beerland είναι ένας χρονοπρογραμματιστής σχεδιασμένος να δίνει προτεραιότητα στην τοπικότητα (locality) και την κλιμακωσιμότητα (scalability).

Δίνει προτεραιότητα στη διατήρηση των διεργασιών στην ίδια CPU για να διατηρείται η τοπικότητα της προσωρινής μνήμης (cache locality), εξασφαλίζοντας παράλληλα καλή κλιμακωσιμότητα σε πολλές CPU με τη χρήση τοπικών DSQs (ουρές εκτέλεσης ανά CPU) όταν το σύστημα δεν είναι κορεσμένο.

- Περιπτώσεις χρήσης:
  - Φόρτοι εργασίας με εντατική χρήση προσωρινής μνήμης (cache)
  - Συστήματα με μεγάλο αριθμό CPU
  - Παιχνίδια (Gaming): Λειτουργεί εκπληκτικά καλά σε ορισμένα παιχνίδια, αν και τα αποτελέσματα ενδέχεται να διαφέρουν.
  - Διακομιστής (Server): Κατάλληλος για γενικής χρήσης φόρτους εργασίας διακομιστή λόγω των βελτιστοποιήσεων κλιμακωσιμότητας και τοπικότητας.
  - Μπορεί να χρησιμοποιηθεί και για χρήση επιφάνειας εργασίας.

### [scx_bpfland](<https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_bpfland>)

**Ανάπτυξη από: Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

Έτοιμο για παραγωγική χρήση; <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

Ένας χρονοπρογραμματιστής sched_ext βασισμένος στο `vruntime` που δίνει προτεραιότητα στους διαδραστικούς φόρτους εργασίας. Εξαιρετικά ευέλικτος και εύκολος στην προσαρμογή.

Το Bpfland, όταν λαμβάνει αποφάσεις για το ποιοι πυρήνες θα χρησιμοποιηθούν, λαμβάνει υπόψη τη διάταξη της προσωρινής τους μνήμης και το ποιοι πυρήνες μοιράζονται την ίδια προσωρινή μνήμη L2/L3, οδηγώντας σε λιγότερες αστοχίες προσωρινής μνήμης (cache misses) = υψηλότερες επιδόσεις.

- Περιπτώσεις χρήσης:
  - Παιχνίδια (Gaming)
  - Χρήση επιφάνειας εργασίας
  - Πολυμέσα/Παραγωγή ήχου
  - Εξαιρετική διαδραστικότητα υπό εντατικούς φόρτους εργασίας
  - Εξοικονόμηση ενέργειας
  - Διακομιστής (Server)

#### Λειτουργίες χρονοπρογραμματιστή

##### Low Latency (Χαμηλή καθυστέρηση)

* **Παράμετροι γραμμής εντολών:** `-m performance -w`
* **Περιγραφή:** Προορίζεται για τη μείωση της καθυστέρησης εις βάρος της συνολικής διεκπεραιωτικότητας (throughput). Κατάλληλο για εφαρμογές ήπιου πραγματικού χρόνου, όπως η επεξεργασία ήχου και τα πολυμέσα.

##### Power Save (Εξοικονόμηση ενέργειας)

* **Παράμετροι γραμμής εντολών:** `-s 20000 -m powersave -I 100 -t 100`
* **Περιγραφή:** Δίνει προτεραιότητα στην ενεργειακή απόδοση. Προτιμά τους λιγότερο αποδοτικούς πυρήνες (π.χ. E-cores στην Intel).

##### Server (Διακομιστής)

* **Παράμετροι γραμμής εντολών:** `-s 20000 -S`
* **Περιγραφή:** Δίνει προτεραιότητα σε διεργασίες με αυστηρή συνάφεια (strict affinity). Αυτή η επιλογή μπορεί να αυξήσει τη διεκπεραιωτικότητα εις βάρος της καθυστέρησης και είναι πιο κατάλληλη για φόρτους εργασίας διακομιστή.

### [scx_cake](https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_cake)

**Ανάπτυξη από: RitzDaCat (RitzDaCat [GitHub](<https://github.com/RitzDaCat>))**

- Έτοιμο για παραγωγική χρήση; <Icon name="information" color="var(--sl-color-text-accent)" size="2rem" />

Το `scx_cake` είναι ένας πειραματικός χρονοπρογραμματιστής CPU σε BPF που προσαρμόζει τον αλγόριθμο DRR++ (Deficit Round Robin++) του δικτυακού [CAKE](https://www.bufferbloat.net/projects/codel/wiki/Cake/) για τον χρονοπρογραμματισμό CPU.
- Ταξινόμηση 4 επιπέδων — Οι διεργασίες ταξινομούνται βάσει του `avg_runtime` EWMA σε Critical / Interactive / Frame / Bulk
- Μηδενικές καθολικές ατομικές λειτουργίες — Πίνακες BSS ανά CPU με εγγραφές προστατευμένες από MESI εξαλείφουν το κλείδωμα διαύλου (bus locking)
- Επιλογή αδρανούς CPU ανατεθειμένη στον πυρήνα — `scx_bpf_select_cpu_dfl()` για έγκυρη επιλογή CPU χωρίς παρωχημένα δεδομένα
- Κατακερματισμός DSQ ανά LLC — Εξαλείφει τη διαμάχη κλειδώματος (lock contention) μεταξύ CCD σε επεξεργαστές πολλαπλών chiplet
- Παρακολούθηση ελλείμματος DRR++ — Ο αλγόριθμος δικαιοσύνης ροής του δικτυακού CAKE προσαρμοσμένος για χρονοπρογραμματισμό διεργασιών CPU

Σχεδιασμένος για φόρτους εργασίας παιχνιδιών σε σύγχρονο υλικό AMD και Intel.

- Περιπτώσεις χρήσης:
  - Παιχνίδια (Gaming)

#### Σύστημα 4 επιπέδων (4-Tier System)

Το `scx_cake` ταξινομεί κάθε διεργασία σε ένα από τέσσερα επίπεδα βάσει του χρόνου εκτέλεσης **EWMA** (Εκθετικός Κινητός Μέσος Όρος / Exponential Weighted Moving Average). Η ταξινόμηση είναι αυτόματη και συνεχής — οι διεργασίες μετακινούνται μεταξύ των επιπέδων καθώς αλλάζει η συμπεριφορά τους.

##### Όρια επιπέδων (Tier Gates)

| Επίπεδο | Όνομα       | avg_runtime | Τυπικός φόρτος εργασίας                                   | Quantum | Starvation |
| :------ | :---------- | :---------- | :-------------------------------------------------------- | :------ | :--------- |
| **T0**  | Critical    | < 100µs     | Χειριστές IRQ, οδηγοί εισόδου, ήχος (PipeWire), δίκτυο    | 0.5ms   | 3ms        |
| **T1**  | Interactive | < 2ms       | Compositors, φυσική παιχνιδιών, AI παιχνιδιών, σύντομα νήματα | 2.0ms   | 8ms        |
| **T2**  | Frame       | < 8ms       | Νήματα απόδοσης (render) παιχνιδιών, κωδικοποίηση βίντεο  | 4.0ms   | 40ms       |
| **T3**  | Bulk        | ≥ 8ms       | Μεταγλώττιση, ευρετηρίαση παρασκηνίου, μαζικές εργασίες   | 8.0ms   | 100ms      |

:::tip
**Καμία διεργασία παιχνιδιού δεν θα πρέπει να βρίσκεται στο T3**. Τα νήματα απόδοσης (render) των παιχνιδιών εκτελούνται για 2-8ms ανά καρέ → T2. Η φυσική και η AI εκτελούνται για 0.5-2ms → T1. Οι χειριστές εισόδου εκτελούνται < 100µs → T0. Μόνο διεργασίες που εκτελούν αδιάκοπη εργασία CPU άνω των 8ms (μεταγλώττιση shader, οθόνες φόρτωσης) καταλήγουν στο T3.
:::

##### Πώς λειτουργεί η ταξινόμηση

1. **Αρχική τοποθέτηση**: Βασίζεται στην τιμή `nice` — `nice < 0` → T0, `nice 0-10` → T1, `nice > 10` → T3
2. **Εγκυρότητα χρόνου εκτέλεσης**: Μετά από ~3 διακοπές, το `avg_runtime` EWMA καθίσταται καθοριστικό. Μια διεργασία με `nice -5` που εκτελεί ριπές των 50ms θα επαναταξινομηθεί στο T3 ανεξάρτητα από την τιμή `nice`.
3. **Υστέρηση (Hysteresis)**: Μια νεκρή ζώνη (deadband) 10% αποτρέπει τις ταλαντώσεις στα όρια των επιπέδων. Η αναβάθμιση απαιτεί το `avg_runtime` να είναι σαφώς κάτω από το όριο· ο υποβιβασμός είναι άμεσος.
4. **Κλιμακωτή αναβολή (Graduated backoff)**: Μόλις ένα επίπεδο παραμείνει σταθερό για 3+ διαδοχικές διακοπές, η συχνότητα επαναταξινόμησης μειώνεται ανά επίπεδο: το T0 επανελέγχεται κάθε 1024η διακοπή, το T3 κάθε 16η. Η αστάθεια επαναφέρει τον έλεγχο στην πλήρη συχνότητα.

##### Παρακολούθηση ελλείμματος DRR++

Προσαρμοσμένη από τη δικαιοσύνη ροής του δικτυακού CAKE:

- Κάθε διεργασία ξεκινά με ένα **έλλειμμα** (quantum + μπόνους νέας ροής ≈ πίστωση 10ms)
- Κάθε περίοδος εκτέλεσης καταναλώνει έλλειμμα ανάλογα με τον χρόνο εκτέλεσης
- Όταν εξαντληθεί το έλλειμμα → αφαιρείται το μπόνους νέας ροής → η διεργασία ανταγωνίζεται κανονικά
- Αυτό προσφέρει στα νεοδημιουργηθέντα νήματα (π.χ. όταν ένα παιχνίδι εκκινεί ένα νήμα εργασίας) άμεση ανταπόκριση που φθίνει σταδιακά με φυσικό τρόπο

##### DVFS (Κλιμάκωση συχνότητας CPU)

Κάθε επίπεδο αντιστοιχίζεται σε έναν στόχο επιδόσεων CPU μέσω ενός πίνακα αναζήτησης RODATA:

| Επίπεδο | Στόχος               | Αιτιολόγηση                                                                    |
| :------ | :------------------- | :----------------------------------------------------------------------------- |
| T0-T2   | 100% (μέγιστη συχν.) | Οι φόρτοι εργασίας παιχνιδιών χρειάζονται πλήρεις επιδόσεις                    |
| T3      | 75%                  | Οι εργασίες παρασκηνίου μπορούν να εκτελούνται ελαφρώς πιο αργά για εξοικονόμηση ενέργειας |

Σε υβριδικές CPU της Intel (`has_hybrid = true`), οι στόχοι κλιμακώνονται ανάλογα με το `cpuperf_cap` κάθε πυρήνα, ώστε να αποφεύγεται η υπερβολική ζήτηση συχνότητας στους πυρήνες E-cores.

#### Ορίσματα γραμμής εντολών (CLI)

| Όρισμα                    | Προεπιλογή | Περιγραφή                               |
| :------------------------ | :--------- | :-------------------------------------- |
| `--verbose, -v`           | `false`    | Ενεργοποίηση ζωντανής προβολής στατιστικών TUI |

### [scx_cosmos](https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_cosmos)

**Ανάπτυξη από: Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

- Έτοιμο για παραγωγική χρήση; <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

Ελαφρύς χρονοπρογραμματιστής βελτιστοποιημένος για τη διατήρηση της τοπικότητας διεργασίας-προς-CPU.

Όταν το σύστημα δεν είναι κορεσμένο, ο χρονοπρογραμματιστής δίνει προτεραιότητα στη διατήρηση των διεργασιών στην ίδια CPU χρησιμοποιώντας τοπικές DSQs. Αυτό όχι μόνο διατηρεί την τοπικότητα, αλλά μειώνει και τη διαμάχη κλειδώματος (locking contention) σε σύγκριση με τις κοινόχρηστες DSQs, επιτρέποντας καλή κλιμακωσιμότητα σε πολλές CPU.

- Περιπτώσεις χρήσης:
  - Χρονοπρογραμματιστής γενικής χρήσης: ο χρονοπρογραμματιστής προσαρμόζεται τόσο για φόρτους εργασίας διακομιστή όσο και για φόρτους εργασίας επιφάνειας εργασίας.

#### Λειτουργίες χρονοπρογραμματιστή

##### Auto (Αυτόματο)

* **Παράμετροι γραμμής εντολών:** Καμία.
* **Περιγραφή:**

##### Gaming (Παιχνίδια)

* **Παράμετροι γραμμής εντολών:** `-s 700 -S`
* **Περιγραφή:** Θυσιάζει τη διεκπεραιωτικότητα για καλύτερη συνέπεια στις επιδόσεις παιχνιδιών, μειώνοντας τη διαμάχη σε κοινόχρηστους πυρήνες SMT.

##### Power Save (Εξοικονόμηση ενέργειας)

* **Παράμετροι γραμμής εντολών:** `-m powersave`
* **Περιγραφή:** Δίνει προτεραιότητα στην ενεργειακή απόδοση. Προτιμά τους λιγότερο αποδοτικούς πυρήνες (π.χ. E-cores στην Intel).

##### Low Latency (Χαμηλή καθυστέρηση)

* **Παράμετροι γραμμής εντολών:** `-s 700 -S -m performance -w`
* **Περιγραφή:** Προορίζεται για τη μείωση της καθυστέρησης εις βάρος της διεκπεραιωτικότητας. Κατάλληλο για εφαρμογές ήπιου πραγματικού χρόνου, όπως η επεξεργασία ήχου και τα πολυμέσα. Παρέχει πιο ομοιόμορφη κατανομή φόρτου στους διαθέσιμους πυρήνες θυσιάζοντας την ενεργειακή απόδοση.

##### Server (Διακομιστής)

* **Παράμετροι γραμμής εντολών:** `-s 20000 -c 75 -p 250`
* **Περιγραφή:** Ενεργοποιεί τη συνάφεια χώρου διευθύνσεων (address space affinity) για τη βελτίωση της τοπικότητας και των επιδόσεων σε ορισμένους φόρτους εργασίας που είναι ευαίσθητοι στην προσωρινή μνήμη. Η διάρκεια του χρονικού μεριδίου (slice) ορίζεται στα 20ms, μαζί με τη δειγματοληψία (polling) που παρακολουθεί πόσο συχνά ο χρονοπρογραμματιστής συγκρίνει τη χρήση CPU με το όριο απασχόλησης CPU για να αποφασίσει πότε το σύστημα είναι απασχολημένο.

### [scx_flash](<https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_flash>)

**Ανάπτυξη από: Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

Έτοιμο για παραγωγική χρήση; <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

Ένας χρονοπρογραμματιστής που εστιάζει στη διασφάλιση δικαιοσύνης μεταξύ των διεργασιών και στην προβλεψιμότητα των επιδόσεων.

Λειτουργεί χρησιμοποιώντας μια [πολιτική Earliest Deadline First (EDF)](https://www.geeksforgeeks.org/operating-systems/earliest-deadline-first-edf-cpu-scheduling-algorithm/), όπου σε κάθε διεργασία ανατίθεται ένα βάρος «καθυστέρησης» (latency). Αυτό το βάρος προσαρμόζεται δυναμικά με βάση το πόσο συχνά μια διεργασία αποδεσμεύει την CPU πριν εξαντληθεί ολόκληρο το χρονικό της μερίδιο (time slice).

Οι διεργασίες που αποδεσμεύουν νωρίς την CPU λαμβάνουν υψηλότερο βάρος καθυστέρησης, αποκτώντας προτεραιότητα έναντι των διεργασιών που καταναλώνουν πλήρως το χρονικό τους μερίδιο.

- Περιπτώσεις χρήσης:
  - Παιχνίδια (Gaming)
  - Φόρτοι εργασίας ευαίσθητοι στην καθυστέρηση, όπως πολυμέσα ή επεξεργασία ήχου σε πραγματικό χρόνο
  - Ανάγκη για ανταπόκριση υπό συνθήκες υπερφόρτωσης
  - Συνέπεια στις επιδόσεις
  - Διακομιστής (Server)

#### Λειτουργίες χρονοπρογραμματιστή

##### Low Latency (Χαμηλή καθυστέρηση)

* **Παράμετροι γραμμής εντολών:** `-m performance -w -C 0`
* **Περιγραφή:** Προορίζεται για τη μείωση της καθυστέρησης εις βάρος της διεκπεραιωτικότητας. Κατάλληλο για εφαρμογές ήπιου πραγματικού χρόνου, όπως η επεξεργασία ήχου και τα πολυμέσα.

##### Gaming (Παιχνίδια)

* **Παράμετροι γραμμής εντολών:** `-m all`
* **Περιγραφή:** Βελτιστοποιεί για υψηλές επιδόσεις στα παιχνίδια.

##### Power Save (Εξοικονόμηση ενέργειας)

* **Παράμετροι γραμμής εντολών:** `-m powersave -I 10000 -t 10000 -s 10000 -S 1000`
* **Περιγραφή:** Δίνει προτεραιότητα στην ενεργειακή απόδοση. Προτιμά τους λιγότερο αποδοτικούς πυρήνες (π.χ. E-cores στην Intel) και εισάγει έναν αναγκαστικό κύκλο αδράνειας κάθε 10ms για αύξηση της εξοικονόμησης ενέργειας.

##### Server (Διακομιστής)

* **Παράμετροι γραμμής εντολών:** `-m all -s 20000 -S 1000 -I -1 -D -L`
* **Περιγραφή:** Ρυθμισμένο για φόρτους εργασίας διακομιστή. Ανταλλάσσει την ταχύτητα ανταπόκρισης με αυξημένη διεκπεραιωτικότητα.

### [scx_flow](https://github.com/sched-ext/scx/tree/main/scheds/experimental/scx_flow)

**Ανάπτυξη από: Galih Tama (galpt [GitHub](https://github.com/galpt))**

Έτοιμο για παραγωγική χρήση; <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

Το scx_flow είναι ένας χρονοπρογραμματιστής βασισμένος σε προϋπολογισμό (budget) που ταξινομεί τις διεργασίες σε ένα από τέσσερα επίπεδα O(1) FIFO με βάση το πόσο προϋπολογισμό τους απομένει. Χωρίς ευρετικούς κανόνες, χωρίς αλγόριθμους βαθμολόγησης, χωρίς προσαρμοστική ρύθμιση — κάθε απόφαση προέρχεται από έναν μόνο αριθμό: τον *εναπομείναντα προϋπολογισμό*.

- Περιπτώσεις χρήσης:
  - Πολυδιεργασία (multitasking) γενικής χρήσης σε επιφάνεια εργασίας και σταθμό εργασίας
  - Παιχνίδια με ανοιχτές εφαρμογές στο παρασκήνιο
  - Εργασία ανάπτυξης λογισμικού με μεταγλωττίσεις, δοκιμές ή κοντέινερ σε εκτέλεση
  - Κάθε σενάριο όπου έχει σημασία η διαδραστική ανταπόκριση υπό μεικτό φόρτο
  - Συστήματα που χρειάζονται ντετερμινιστικό, εξηγήσιμο χρονοπρογραμματισμό (ενσωματωμένος έλεγχος, ρομποτική, αεροηλεκτρονική)

#### Πώς λειτουργεί — ο προϋπολογισμός (budget)

Σκεφτείτε κάθε διεργασία σαν να έχει έναν «προϋπολογισμό ανταπόκρισης». Όσο μια διεργασία κοιμάται (περιμένοντας κάτι να κάνει), συσσωρεύει προϋπολογισμό. Όταν ξυπνά και εκτελείται, τον ξοδεύει. Οι διεργασίες που ξυπνούν διατηρώντας ακόμη προϋπολογισμό αποτελούν ένδειξη διαδραστικότητας — αποστέλλονται αμέσως στην CPU στην οποία εκτελέστηκαν τελευταία, παρακάμπτοντας εντελώς το σύστημα επιπέδων. Οι διεργασίες που εξαντλούν τον προϋπολογισμό τους επανατοποθετούνται στην ουρά, σε ένα από τα τέσσερα επίπεδα FIFO.

##### Τα τέσσερα επίπεδα αποστολής (dispatch tiers)

Όταν μια διεργασία επανατοποθετείται στην ουρά (όχι κατά την αφύπνιση), ο εναπομείνας προϋπολογισμός της καθορίζει σε ποιο επίπεδο θα καταλήξει:

| Επίπεδο | Όριο προϋπολογισμού | Τι είδους διεργασίες καταλήγουν εδώ |
|---|---|---|
| **Priority** | ≥ 1.5ms | Διαδραστικές διεργασίες που κοιμούνται συχνά και εκτελούνται για λίγο |
| **Normal** | ≥ 1ms | Τυπικές διεργασίες με ικανοποιητικό υπόλοιπο προϋπολογισμού |
| **Low** | ≥ 0.5ms | Διεργασίες με χαμηλό υπόλοιπο προϋπολογισμού |
| **Deficit** | < 0.5ms | Μαζικές διεργασίες (bulk workers), διεργασίες που καταναλώνουν CPU, εργασίες παρασκηνίου |

Κάθε επίπεδο είναι μια απλή ουρά FIFO — εισαγωγή O(1), εξαγωγή O(1). Χωρίς διασχίσεις δέντρων, χωρίς επανυπολογισμούς προτεραιότητας.

##### Χωρίς λιμοκτονία (starvation), χωρίς αντιστροφή προτεραιότητας

Η συνάρτηση αποστολής δεν αδειάζει απλώς το επίπεδο Priority πρώτο κάθε φορά. Περιστρέφει το επίπεδο εκκίνησης σε κάθε κλήση — η έκφραση `gen & 3` αποφασίζει από πού θα ξεκινήσει. Έτσι, το επίπεδο Deficit δεν περιμένει ποτέ περισσότερους από 3 κύκλους αποστολής προτού εξυπηρετηθεί πρώτο. Αυτό σημαίνει ότι οι μαζικές εργασίες σημειώνουν πρόοδο ακόμη και υπό βαρύ διαδραστικό φόρτο, και δεν υπάρχει αντιστροφή προτεραιότητας (priority inversion) επειδή κανένα μεμονωμένο επίπεδο δεν μπορεί να μονοπωλήσει την CPU.

##### Οι αφυπνίσεις παρακάμπτουν εντελώς την ουρά

Όταν μια διεργασία ξυπνά (κοιμόταν και τώρα έχει κάτι να κάνει), δεν περιμένει σε καμία ουρά επιπέδου. Μεταβαίνει απευθείας στην CPU στην οποία εκτελέστηκε τελευταία μέσω του `SCX_DSQ_LOCAL_ON` — με ζεστή την προσωρινή μνήμη και άμεσα. Αυτό είναι που διατηρεί τις διαδραστικές διεργασίες ταχύτατες: μια καρτέλα του Discord ή του προγράμματος περιήγησης που κοιμόταν ξυπνά με προϋπολογισμό και αποστέλλεται σε μικροδευτερόλεπτα, όχι σε χιλιοστά του δευτερολέπτου.

##### Οι καρφιτσωμένες διεργασίες (pinned tasks) προηγούνται πάντα

Οι διεργασίες που δεν μπορούν να μεταναστεύσουν μεταξύ CPU (setaffinity) αποκτούν τη δική τους ουρά FIFO ανά CPU, η οποία έχει απόλυτη προτεραιότητα έναντι οποιουδήποτε επιπέδου. Αποστέλλονται πριν εκτελεστεί οτιδήποτε από το σύστημα επιπέδων στη συγκεκριμένη CPU.

##### Το αποτέλεσμα

Οι διαδραστικές διεργασίες (είσοδος πληκτρολογίου, ενημερώσεις διεπαφής χρήστη, νήματα ήχου, δειγματοληψία δικτύου) σχεδόν πάντα ξυπνούν με προϋπολογισμό και παίρνουν τη λωρίδα ταχείας κυκλοφορίας. Οι βαριές μαζικές εργασίες CPU (μεταγλώττιση, λήψεις αρχείων, ευρετηρίαση παρασκηνίου) εξαντλούν τον προϋπολογισμό τους και καταλήγουν στο επίπεδο Deficit, όπου εξακολουθούν να σημειώνουν πρόοδο χάρη στην κυκλική αποστολή. Δεν απαιτείται καμία ρύθμιση.

##### Χωρίς προφίλ, χωρίς αυτόματη ρύθμιση, χωρίς λειτουργίες

Το `scx_flow` **δεν** διαθέτει λειτουργίες Gaming, Power Save ή Low Latency — και, σε αντίθεση με παλαιότερες εκδόσεις, δεν διαθέτει επίσης προσαρμοστικό βρόχο ελέγχου. Η κυκλική αποστολή επιπέδων και τα όρια προϋπολογισμού είναι σταθερές χρόνου μεταγλώττισης. Αυτό που λαμβάνετε είναι αυτό που εκτελείται: ντετερμινιστικό, εξηγήσιμο και πανομοιότυπο σε κάθε σύστημα. Εάν μια διεργασία έχει προϋπολογισμό, λαμβάνει προτεραιότητα. Εάν δεν έχει, μοιράζεται δίκαια το επίπεδο Deficit. Αυτή είναι ολόκληρη η πολιτική του.

#### Διεπαφή ιστού (Web UI)

Όταν εκκινεί το `scx_flow`, εξυπηρετεί αυτόματα έναν ζωντανό πίνακα μετρήσεων στη διεύθυνση **[http://localhost:50005](http://localhost:50005)**. Ανοίξτε τον σε οποιοδήποτε πρόγραμμα περιήγησης — δεν χρειάζονται επιπλέον παράμετροι.

Ο πίνακας ελέγχου εμφανίζει:
- Πόσες αποστολές (dispatches) έχουν περάσει από κάθε επίπεδο (Priority / Normal / Low / Deficit)
- Πληροφορίες συστήματος: εκτελούμενες διεργασίες, χρόνος λειτουργίας (uptime), συνολικός αριθμός αποστολών
- Μια μπάρα κατανομής επιπέδων ώστε να βλέπετε με μια ματιά αν κυριαρχεί ο διαδραστικός ή ο μαζικός φόρτος εργασίας
- Κάθε κάρτα μέτρησης είναι διαδραστική (clickable) — ανοίγει ένα παράθυρο ιστορικού με γραφήματα sparkline και ραβδόγραμμα
- Όλες οι τιμές ενημερώνονται κάθε δευτερόλεπτο μέσω polling — δεν απαιτείται ανανέωση της σελίδας

Εάν η σελίδα δεν φορτώνει, ο χρονοπρογραμματιστής ενδέχεται να έχει σταματήσει να εκτελείται (ο πυρήνας επιστρέφει στον ενσωματωμένο EEVDF).

```sh
# Απενεργοποιήστε τη διεπαφή ιστού αν δεν τη χρειάζεστε:
sudo scx_flow --no-webui
```

Όταν το `scx_loader` εκτελείται με αυστηροποίηση του systemd (systemd hardening) που περιορίζει τις οικογένειες υποδοχών (`RestrictAddressFamilies`, `SocketBindDeny`), η δέσμευση TCP μπλοκάρεται και το scx_flow καταφεύγει σε ένα Unix socket στη διαδρομή `/tmp/scx_flow.sock`. Σε αυτήν την περίπτωση, το πρόγραμμα περιήγησης δεν μπορεί να προσπελάσει απευθείας τον πίνακα ελέγχου — εκτελέστε προσωρινά `sudo scx_flow --no-webui` για να σιγήσετε τα σφάλματα εάν δεν χρειάζεστε τη διεπαφή χρήστη.

#### Ορίσματα γραμμής εντολών (CLI)

| Όρισμα | Περιγραφή |
|---|---|
| `--no-webui` | Απενεργοποίηση της ενσωματωμένης διεπαφής ιστού |
| `-d, --debug` | Ενεργοποίηση καταγραφής επιπέδου αποσφαλμάτωσης (debug) |
| `-V, --version` | Εκτύπωση της έκδοσης του χρονοπρογραμματιστή και έξοδος |

:::note
Το `scx_flow` **δεν** διαθέτει λειτουργίες προφίλ για το `scx_loader` (Gaming, Power Save, Low Latency, Server). Κάθε απόφαση χρονοπρογραμματισμού προκύπτει απευθείας από τον προϋπολογισμό της διεργασίας — δεν χρειάζονται προφίλ.
:::

### ananicy-cpp και sched-ext

:::note[Ενημέρωση σχετικά με τα ananicy-cpp και sched-ext]
Μετά από περαιτέρω ανάπτυξη των χρονοπρογραμματιστών, το ananicy-cpp είναι συνήθως ασφαλές να χρησιμοποιείται παράλληλα με αυτούς. Ωστόσο, εάν αντιμετωπίσετε κολλήματα (stalls) ή αστάθεια, εξετάστε το ενδεχόμενο να το απενεργοποιήσετε ως βήμα αντιμετώπισης προβλημάτων.
:::

Για να απενεργοποιήσετε/διακόψετε το `ananicy-cpp`, εκτελέστε την ακόλουθη εντολή:

```sh
systemctl disable --now ananicy-cpp
```

### Εναλλαγή προφίλ ισχύος μέσω του scx_loader

Υλοποιείται στο πακέτο `power-profiles-daemon` που παρέχεται από το CachyOS, το οποίο περιλαμβάνει ένα [προσαρμοσμένο patch](https://github.com/CachyOS/CachyOS-PKGBUILDS/blob/master/power-profiles-daemon/0001-Add-support-for-scx_loader-modes-switching.patch) για την υποστήριξη εναλλαγής προφίλ ισχύος του `scx_loader`.

- Εάν το `scx_loader` εκτελείται ήδη, όταν χρησιμοποιείται το [game-performance](/el/configuration/gaming#εναλλαγή-προφίλ-ισχύος-κατ-απαίτηση), θα αλλάζει αυτόματα τον ενεργό χρονοπρογραμματιστή στο προφίλ `Gaming` κατά την εκκίνηση ενός παιχνιδιού και θα επανέρχεται στο προεπιλεγμένο προφίλ όταν το παιχνίδι κλείσει.
- Κατά την αλλαγή μεταξύ προφίλ ισχύος, π.χ. στο KDE Plasma ή στο GNOME χρησιμοποιώντας τον επιλογέα προφίλ ισχύος, το `scx_loader` θα μεταβαίνει αυτόματα στο αντίστοιχο προφίλ χρονοπρογραμματιστή:

| Προφίλ ισχύος       | Προφίλ χρονοπρογραμματιστή |
| ------------------- | -------------------------- |
| Power Saver         | Power Save                 |
| Balanced            | Auto                       |
| Performance         | Gaming                     |

### Συγκριτικές δοκιμές και αξιολόγηση χρονοπρογραμματιστών με το cachyos-benchmarker

Το εργαλείο [cachyos-benchmarker](https://github.com/CachyOS/cachyos-benchmarker) παρέχει έναν εύκολο τρόπο για να αξιολογείτε και να συγκρίνετε τις επιδόσεις διαφορετικών χρονοπρογραμματιστών CPU.

Εκτελεί μια ολοκληρωμένη σουίτα δοκιμών επιδόσεων (benchmarks) για τη μέτρηση των επιδόσεων της CPU, της μνήμης και του συνολικού συστήματος υπό διάφορους φόρτους εργασίας.

Περιλαμβάνονται οι ακόλουθες δοκιμές:

| Δοκιμή                      | Μετράει                                       | Εργαλείο     |
| --------------------------- | --------------------------------------------- | ------------ |
| **stress-ng cpu-cache-mem** | Επιδόσεις CPU, cache και μνήμης               | `stress-ng`  |
| **FFmpeg compilation**      | Επιδόσεις παράλληλης μεταγλώττισης            | `make`       |
| **x265 encoding**           | Διεκπεραιωτικότητα κωδικοποίησης βίντεο       | `x265`       |
| **argon2 hashing**          | Πολυνηματικό hashing κωδικών πρόσβασης        | `argon2`     |
| **perf sched msg**          | Εναλλαγή περιβάλλοντος και επιδόσεις IPC      | `perf`       |
| **perf memcpy**             | Διεκπεραιωτικότητα μνήμης `memcpy()`          | `perf`       |
| **prime calculation**       | Αριθμητική ακεραίων και παραλληλισμός         | `primesieve` |
| **NAMD**                    | Μοριακή δυναμική (επιστημονικός φόρτος)       | `namd3`      |
| **Blender render**          | Απόδοση 3D αποκλειστικά με CPU                | `blender`    |
| **xz compression**          | Διεκπεραιωτικότητα συμπίεσης                  | `xz`         |
| **Kernel defconfig build**  | Επιδόσεις μεταγλώττισης πυρήνα                | `make`       |
| **y-cruncher**              | Μαθηματική ακρίβεια και καταπόνηση μνήμης     | `y-cruncher` |

Το `cachyos-benchmarker` μπορεί να χρησιμοποιηθεί για διάφορους σκοπούς, όπως:

- **Έλεγχος σταθερότητας χρονοπρογραμματιστή**
  Εκτελέστε την πλήρη σουίτα δοκιμών για να εντοπίσετε κολλήματα, καταρρεύσεις (crashes) ή υποβαθμίσεις που προκαλούνται από αλλαγές στον χρονοπρογραμματιστή.
  Εάν χρησιμοποιείτε το `scx_loader`, μπορείτε να συλλέξετε αρχεία καταγραφής σε περίπτωση κολλήματος ή κατάρρευσης με την εντολή:
  ```bash
  journalctl --unit scx_loader.service --boot 0 > crash.log
  ```
  Αυτό θα δημιουργήσει ένα αρχείο με όνομα `crash.log` στον τρέχοντα κατάλογό σας.
- **Σύγκριση επιδόσεων χρονοπρογραμματιστών**
  - Αξιολογήστε τις διαφορές επιδόσεων μεταξύ χρονοπρογραμματιστών, π.χ. `BPFLAND vs LAVD`.
- **Μέτρηση της επίδρασης ενημερώσεων πυρήνα ή χρονοπρογραμματιστή**
  - Συγκρίνετε εκτελέσεις πριν και μετά την εφαρμογή patches ή αλλαγών έκδοσης, για να ελέγξετε για υποβαθμίσεις ή βελτιώσεις επιδόσεων.
- **Δοκιμή προσαρμογών διαμόρφωσης**
  - Αξιολογήστε τον αντίκτυπο αλλαγών, όπως οι ρυθμίσεις του ρυθμιστή (governor) CPU, η ενεργοποίηση/απενεργοποίηση SMT ή οι τροποποιημένες παράμετροι χρονοπρογραμματιστή.

#### Απαιτήσεις
- 4 GB μνήμης RAM ή περισσότερο
- Τουλάχιστον 8 GB ελεύθερου χώρου αποθήκευσης
- Χρόνος και υπομονή — **η πλήρης δοκιμή επιδόσεων μπορεί να διαρκέσει πάνω από μία ώρα σε πιο αργά συστήματα**

### Δοκιμή καθυστέρησης χρονοπρογραμματιστή με το schbench

Το schbench είναι ένα εργαλείο μέτρησης επιδόσεων (benchmark) χρονοπρογραμματιστή, σχεδιασμένο για τη μέτρηση της καθυστέρησης του χρονοπρογραμματιστή υπό προσομοιωμένο φόρτο εργασίας διακομιστή. Δημιουργεί έναν παραμετροποιήσιμο αριθμό νημάτων «εργασίας» (worker) και «μηνυμάτων» (message), όπου τα μηνύματα αφυπνίζουν επανειλημμένα τα νήματα εργασίας. Μετρώντας την κατανομή καθυστέρησης από την αφύπνιση έως την εκτέλεση αυτών των νημάτων εργασίας, παρέχει κρίσιμες πληροφορίες για την ικανότητα του πυρήνα να χειρίζεται αφυπνίσεις νημάτων, εξισορρόπηση φόρτου και διαμάχη CPU, ειδικά υπό υψηλό φόρτο.

#### Περιπτώσεις χρήσης

Μπορείτε να χρησιμοποιήσετε το `schbench` για να:

- **Αξιολογήσετε την καθυστέρηση του χρονοπρογραμματιστή:** Εντοπίστε πόσο γρήγορα προγραμματίζονται τα νήματα μετά την αφύπνισή τους.
- **Συγκρίνετε τις επιδόσεις αφύπνισης μεταξύ χρονοπρογραμματιστών:** Ανιχνεύστε βελτιώσεις ή υποβαθμίσεις στην εναλλαγή περιβάλλοντος και στην καθυστέρηση αφύπνισης.
- **Δοκιμάσετε την επίδραση διορθώσεων πυρήνα ή χρονοπρογραμματιστή:** Αξιολογήστε εάν οι ρυθμίσεις ή οι ενημερώσεις επηρεάζουν τη δικαιοσύνη και την ανταπόκριση του χρονοπρογραμματισμού.

#### Εγκατάσταση

Το `schbench` είναι διαθέσιμο στα αποθετήρια του CachyOS:
```bash
sudo pacman -S schbench
```

#### Εκτέλεση της δοκιμής επιδόσεων

Ένας απλός τρόπος για να εκτελέσετε το `schbench` για μια γενική δοκιμή καθυστέρησης είναι:
```bash
schbench -m 2 -t 8 -r 60
```

Αυτό το παράδειγμα εκτελεί:
- 2 νήματα μηνυμάτων (`-m 2`)
- 8 νήματα εργασίας ανά νήμα μηνυμάτων (`-t 8`)
- για συνολική διάρκεια εκτέλεσης 60 δευτερολέπτων (`-r 60`)

Μπορείτε να προσαρμόσετε αυτές τις τιμές ανάλογα με τον αριθμό των πυρήνων της CPU σας και το επιθυμητό επίπεδο φόρτου.

Ακολουθεί ένας πίνακας που επεξηγεί μερικές από τις βασικές επιλογές:

| Επιλογή                      | Περιγραφή                                                                         |
| ---------------------------- | --------------------------------------------------------------------------------- |
| `-C, --calibrate`            | Εκτέλεση βαθμονόμησης και αναφορά χρονισμών (χωρίς benchmark).                    |
| `-L, --no-locking`           | Απενεργοποίηση των spinlocks κατά την εργασία CPU (προεπιλογή: κλείδωμα ενεργό).   |
| `-m, --message-threads <n>`  | Αριθμός νημάτων μηνυμάτων (προεπιλογή: 1).                                        |
| `-t, --threads <n>`          | Νήματα εργασίας ανά νήμα μηνυμάτων (προεπιλογή: αριθμός των CPU).                 |
| `-r, --runtime <sec>`        | Διάρκεια του benchmark (προεπιλογή: 30).                                          |
| `-F, --cache_footprint <KB>` | Μέγεθος αποτυπώματος προσωρινής μνήμης (προεπιλογή: 256).                         |
| `-n, --operations <count>`   | Αριθμός λειτουργιών «think time» προς εκτέλεση (προεπιλογή: 5).                   |
| `-A, --auto-rps`             | Αυτόματη αύξηση του RPS μέχρι να επιτευχθεί ο στόχος χρήσης CPU.                  |
| `-R, --rps <count>`          | Λειτουργία αιτημάτων ανά δευτερόλεπτο (RPS).                                      |
| `-p, --pipe <bytes>`         | Προσομοίωση δοκιμής μεταφοράς μέσω pipe.                                          |
| `-w, --warmuptime <sec>`     | Διάρκεια προθέρμανσης πριν από τη συλλογή στατιστικών (προεπιλογή: 0).            |
| `-i, --intervaltime <sec>`   | Διάστημα εκτύπωσης καθυστερήσεων (προεπιλογή: 10).                                |
| `-z, --zerotime <sec>`       | Διάστημα μηδενισμού στατιστικών καθυστέρησης (προεπιλογή: ποτέ).                  |

##### Πώς να ερμηνεύσετε τα αποτελέσματα

- **Wakeup Latencies (Καθυστερήσεις αφύπνισης):**
  - Μετρά πόσο γρήγορα αφυπνίζονται τα νήματα αφού λάβουν σήμα.
    - Χαμηλότερες τιμές εδώ (ειδικά στο **99ο εκατοστημόριο**) σημαίνουν ότι ο χρονοπρογραμματιστής ανταποκρίνεται ταχύτερα.
- **Request Latencies (Καθυστερήσεις αιτημάτων):**
  - Αντιπροσωπεύει τον χρόνο που απαιτείται για την ολοκλήρωση αιτημάτων μεταξύ νημάτων.
    - Η χαμηλότερη καθυστέρηση υποδηλώνει καλύτερη επικοινωνία μεταξύ νημάτων και αποδοτικότητα χρονοπρογραμματισμού.
- **RPS (Αιτήματα ανά δευτερόλεπτο):**
  - Δείχνει τη διατηρήσιμη διεκπεραιωτικότητα:
    - Ένα υψηλότερο **μέσο RPS** υποδηλώνει ότι ο χρονοπρογραμματιστής μπορεί να διεκπεραιώσει περισσότερη εργασία ανά δευτερόλεπτο υπό τη δεδομένη διαμόρφωση.

Συμπερασματικά:
- Ένας **καλός χρονοπρογραμματιστής** θα εμφανίζει **χαμηλές καθυστερήσεις αφύπνισης και αιτημάτων** με **σταθερό RPS**.
- Ένας **λιγότερο αποδοτικός χρονοπρογραμματιστής** ενδέχεται να παρουσιάζει **υψηλές αιχμές καθυστέρησης** ή **ασταθείς τιμές RPS** με την πάροδο του χρόνου.

:::note
Αυτά τα αποτελέσματα ενδέχεται να διαφέρουν ανάλογα με την CPU, τον αριθμό πυρήνων, το φόρτο του συστήματος και το εάν ο χρονοπρογραμματιστής είναι σε θέση να χειριστεί αποδοτικά την αρχιτεκτονική της CPU σας.
:::

### Συστάσεις για συγκριτικές δοκιμές (benchmarking) σε παιχνίδια

Εάν επιθυμείτε να πραγματοποιήσετε δοκιμές επιδόσεων σε παιχνίδια για να συγκρίνετε την απόδοση διαφορετικών χρονοπρογραμματιστών, ακολουθούν μερικές συμβουλές για να λάβετε τα πιο ακριβή αποτελέσματα:

- **Χρησιμοποιήστε ενσωματωμένα εργαλεία δοκιμών (benchmarks):** Πολλά σύγχρονα παιχνίδια διαθέτουν ενσωματωμένα εργαλεία benchmarking. Αυτά είναι σχεδιασμένα ώστε να παρέχουν συνεπή αποτελέσματα εκτελώντας την ίδια ακολουθία γεγονότων κάθε φορά.
  - Δείτε αυτόν τον [ιστότοπο](https://www.pcgamingwiki.com/wiki/List_of_games_with_built-in_benchmarks) για μια λίστα παιχνιδιών που περιλαμβάνουν ενσωματωμένα benchmarks.
- **Συνεπείς ρυθμίσεις:** Βεβαιωθείτε ότι οι ρυθμίσεις του παιχνιδιού (ανάλυση, ποιότητα γραφικών κ.λπ.) είναι ίδιες για κάθε δοκιμαστική εκτέλεση.
- **Κλείστε τις εφαρμογές παρασκηνίου:** Άλλες εφαρμογές που εκτελούνται στο παρασκήνιο μπορούν να επηρεάσουν τις επιδόσεις. Κλείστε τα περιττά προγράμματα για να ελαχιστοποιήσετε τον αντίκτυπό τους.
- Εάν δεν χρησιμοποιείτε ενσωματωμένο benchmark, προσπαθήστε να εκτελείτε τις ίδιες ενέργειες στο παιχνίδι για κάθε δοκιμή. Αυτό μπορεί να περιλαμβάνει την ίδια διαδρομή, παρόμοια σενάρια μάχης ή την εκτέλεση των ίδιων ενεργειών.
  - Ακόμη και το να μην στοχεύετε στο ίδιο σημείο μπορεί να οδηγήσει σε διαφορετικά αποτελέσματα επιδόσεων.
- **Πολλαπλές εκτελέσεις:** Εκτελέστε πολλαπλές δοκιμές του benchmark και υπολογίστε τον μέσο όρο για να αντισταθμίσετε τυχόν διακυμάνσεις.
- **Χρησιμοποιήστε εργαλεία παρακολούθησης επιδόσεων:** Εργαλεία όπως το MangoHud ή το GOverlay μπορούν να παρέχουν μετρήσεις επιδόσεων σε πραγματικό χρόνο, όπως FPS, χρόνους καρέ (frame times) και χρήση CPU/GPU.
- **Αξιοποιήστε συντομεύσεις πληκτρολογίου ή μακροεντολές:**
  - Ένα παράδειγμα είναι η δημιουργία ενός συνδυασμού πλήκτρων με τον οποίο μπορείτε να κάνετε εναλλαγή μεταξύ διαφορετικών χρονοπρογραμματιστών ή να αλλάζετε τις λειτουργίες τους επί τόπου ενώ παίζετε.
    - Αυτό μπορεί να γίνει χρησιμοποιώντας ένα εργαλείο όπως το [scxctl](/el/configuration/sched-ext#εκκίνηση-και-διαχείριση-του-χρονοπρογραμματιστή) ή δημιουργώντας προσαρμοσμένες δέσμες ενεργειών που αλλάζουν τον ενεργό χρονοπρογραμματιστή και τη λειτουργία του.

#### Μεταφόρτωση και κοινοποίηση των δοκιμών σας

Αυτός ο [ιστότοπος](https://flightlesssomething.ambrosia.one/benchmarks) περιέχει μια λίστα δοκιμών επιδόσεων που έχουν πραγματοποιηθεί από την κοινότητα χρησιμοποιώντας διαφορετικούς χρονοπρογραμματιστές ή δοκιμάζοντας διάφορες ρυθμίσεις.

Για να μεταφορτώσετε τα δικά σας benchmarks, θα πρέπει να συνδέσετε τον λογαριασμό σας στο Discord με τον ιστότοπο και έπειτα μπορείτε να υποβάλετε τα δικά σας αποτελέσματα.

Στη συνέχεια, κάντε κλικ στο κουμπί `New benchmark` και συμπληρώστε τις απαιτούμενες πληροφορίες.

- Μπορείτε να μεταφορτώσετε πολλαπλά αποτελέσματα για το ίδιο παιχνίδι χρησιμοποιώντας διαφορετικούς χρονοπρογραμματιστές ή ρυθμίσεις.
- Δέχεται αρχεία καταγραφής τόσο από MangoHud όσο και από Afterburner.
- Επιτρέπει την αναζήτηση βάσει τίτλου ή περιγραφής.

## Ρύθμιση του scx_loader

### Ορισμός χρονοπρογραμματιστή ως προεπιλεγμένου (κατά την εκκίνηση)

Για να ρυθμίσετε έναν χρονοπρογραμματιστή να εκκινεί αυτόματα όταν ξεκινά το `scx_loader` (π.χ. κατά την εκκίνηση του συστήματος), ακολουθήστε αυτά τα βήματα:

<Steps>
1. **Αντιγράψτε το ενδεικτικό αρχείο ρύθμισης** στον κατάλογο ρυθμίσεων:
   ```sh
   sudo mkdir -p /etc/scx_loader
   sudo cp /usr/share/scx_loader/config.toml /etc/scx_loader/config.toml
   ```

2. **Επεξεργαστείτε το αρχείο ρύθμισης** με τον επεξεργαστή κειμένου της προτίμησής σας:
   ```sh
   sudo nano /etc/scx_loader/config.toml
   ```

3. **Ορίστε τον προεπιλεγμένο χρονοπρογραμματιστή και τη λειτουργία**. Για παράδειγμα, για να ορίσετε το `scx_pandemonium` στη λειτουργία `Auto`:
   ```toml
   # Αυτό το πεδίο καθορίζει τον χρονοπρογραμματιστή που θα εκκινεί αυτόματα όταν ξεκινά το scx_loader (π.χ. κατά την εκκίνηση).
   default_sched = "scx_pandemonium"

   # Αυτό το πεδίο καθορίζει τη λειτουργία που θα χρησιμοποιείται όταν ξεκινά το scx_loader (π.χ. κατά την εκκίνηση).
   default_mode = "Auto"
   ```

4. **Ενεργοποιήστε και εκκινήστε την υπηρεσία**:
   ```sh
   sudo systemctl enable --now scx_loader.service
   ```
</Steps>

#### Σειρά αναζήτησης ρυθμίσεων

Το `scx_loader` αναζητά το αρχείο ρύθμισης με την ακόλουθη σειρά:

1. `/etc/scx_loader/config.toml` (Προτιμώμενο)
2. `/etc/scx_loader.toml`
3. `/usr/share/scx_loader/config.toml` (Προεπιλεγμένο πρότυπο)
4. `/usr/share/scx_loader.toml`

### Προσαρμογή ορισμάτων χρονοπρογραμματιστή

Μπορείτε να προσαρμόσετε τα ορίσματα που μεταβιβάζονται σε κάθε χρονοπρογραμματιστή για διαφορετικές λειτουργίες προσθέτοντας μια ενότητα `[scheds.scx_name]` στο αρχείο ρύθμισής σας.

Για λεπτομερείς πληροφορίες και παραδείγματα σχετικά με τον τρόπο ρύθμισης ορισμάτων ανά χρονοπρογραμματιστή, ανατρέξτε στην [τεκμηρίωση ρύθμισης του scx_loader](https://github.com/sched-ext/scx-loader/blob/main/crates/scx_loader/configuration.md).

## Μετάβαση από το scx.service στο scx_loader: Πλήρης οδηγός

:::caution
Μην επιχειρήσετε να εκτελέσετε την υπηρεσία `scx_loader.service` παράλληλα με την υπηρεσία `scx.service`· διαφορετικά, η υπηρεσία φορτωτή θα εκκινηθεί αλλά δεν θα κάνει τίποτα.

Αυτή η σύγκρουση προκύπτει επειδή οι δύο υπηρεσίες δεν γνωρίζουν η μία την ύπαρξη της άλλης, ειδικά όσον αφορά το ποια διαχειρίζεται τους χρονοπρογραμματιστές.
:::

:::tip
Το CachyOS Kernel Manager περιλαμβάνει ήδη ένα [γραφικό περιβάλλον (GUI) για τη διαχείριση του scx_loader.](/el/features/kernel_manager#διαχείριση-του-πλαισίου-sched-ext)
:::

Αρχικά, ας ξεκινήσουμε με μια αναλυτική σύγκριση μεταξύ της δομής του αρχείου `scx.service` και της δομής του αρχείου ρύθμισης του `scx_loader`.

*Εάν είχατε προηγουμένως το LAVD σε εκτέλεση με την παλιά υπηρεσία `scx.service` όπως στο παρακάτω παράδειγμα:*

```sh title='Δομή αρχείου scx.service'
# List of scx_schedulers: scx_bpfland scx_central scx_flash scx_lavd scx_layered scx_nest scx_qmap scx_rlfifo scx_rustland scx_rusty scx_simple scx_userland
SCX_SCHEDULER=scx_lavd

# Ορισμός προσαρμοσμένων παραμέτρων για τον χρονοπρογραμματιστή
SCX_FLAGS='--performance'
```

Τότε το ισοδύναμο στο αρχείο ρύθμισης του `scx_loader` θα έχει την εξής μορφή:

```sh title='Δομή αρχείου scx_loader'
default_sched = "scx_lavd"
default_mode = "Auto"

[scheds.scx_lavd]
auto_mode = ["--performance"]
```

[Για περισσότερες πληροφορίες σχετικά με τον τρόπο ρύθμισης του αρχείου του scx_loader](https://github.com/sched-ext/scx-loader/blob/main/crates/scx_loader/configuration.md#scx_loader-configuration-file)

  Ακολουθήστε τον παρακάτω οδηγό για μια εύκολη μετάβαση από την υπηρεσία `scx systemd service` στο νέο βοηθητικό πρόγραμμα `scx_loader`.
  <Steps>
  1. ```sh title='Απενεργοποίηση του scx.service υπέρ του scx_loader.service'
      systemctl disable --now scx.service && systemctl enable --now scx_loader.service
      ```
  2. ```sh title='Δημιουργία του αρχείου ρύθμισης για το scx_loader και προσθήκη της προεπιλεγμένης δομής'
     # Ο επεξεργαστής Micro θα δημιουργήσει ένα νέο αρχείο.
     sudo micro /etc/scx_loader.toml
     # Προσθέστε τις ακόλουθες γραμμές:

     default_sched = "scx_bpfland" # Επεξεργαστείτε αυτή τη γραμμή με τον χρονοπρογραμματιστή που θέλετε να εκκινεί το scx_loader κατά την εκκίνηση
     default_mode = "Auto" # Πιθανές τιμές: "Auto", "Gaming", "LowLatency", "PowerSave".

     # Πατήστε CTRL + S για να αποθηκεύσετε τις αλλαγές και CTRL + Q για έξοδο από το Micro.
     ```
  3. ```sh title='Επανεκκίνηση του scx_loader'
     systemctl restart scx_loader.service
     ```
     - Έτοιμο· το `scx_loader` θα φορτώνει και θα εκκινεί πλέον τον επιθυμητό χρονοπρογραμματιστή.

  </Steps>

## Συχνές ερωτήσεις (FAQ)

### Υπάρχουν τόσες πολλές επιλογές... γιατί να μην φτιάχνατε απλώς έναν χρονοπρογραμματιστή που να είναι καλός σε όλα;

Ο κύριος λόγος είναι ότι δεν υπάρχει μία ενιαία λύση κατάλληλη για τα πάντα όσον αφορά τον χρονοπρογραμματισμό CPU. Διαφορετικοί φόρτοι εργασίας έχουν διαφορετικές απαιτήσεις και προτεραιότητες, και ένας χρονοπρογραμματιστής που είναι βελτιστοποιημένος για έναν τύπο φόρτου εργασίας ενδέχεται να μην αποδίδει καλά σε έναν άλλον.

Μπορείτε να δείτε τους χρονοπρογραμματιστές CPU σαν διαφορετικά ζευγάρια παπούτσια, καθένα σχεδιασμένο για μια συγκεκριμένη δραστηριότητα. Για παράδειγμα, η εκτέλεση ενός παιχνιδιού σε έναν χρονοπρογραμματιστή βελτιστοποιημένο για φόρτους εργασίας διακομιστή μπορεί να οδηγήσει σε υποβέλτιστες επιδόσεις και αυξημένη καθυστέρηση, ενώ η χρήση ενός χρονοπρογραμματιστή σχεδιασμένου για παιχνίδια σε έναν διακομιστή μπορεί να οδηγήσει σε αναποτελεσματική αξιοποίηση πόρων και μειωμένη διεκπεραιωτικότητα.

Αυτή είναι η μαγεία του `sched-ext`. Οι περιορισμοί δεν αποτελούν πλέον πρόβλημα.

### Γιατί ο χρονοπρογραμματιστής X αποδίδει χειρότερα από τον άλλον;

- Υπάρχουν πολλές μεταβλητές που πρέπει να ληφθούν υπόψη κατά τη σύγκρισή τους. Για παράδειγμα, πώς μετρούν το βάρος μιας διεργασίας; Δίνουν προτεραιότητα στις διαδραστικές διεργασίες έναντι των μη διαδραστικών;
  Τελικά, εξαρτάται από τις σχεδιαστικές τους επιλογές.

### Γιατί όλοι λένε ότι ο χρονοπρογραμματιστής X είναι ο καλύτερος για την περίπτωση X, αλλά δεν αποδίδει τόσο καλά σε εμένα;

- Όπως και στην προηγούμενη απάντηση, η επιλογή της CPU και ο σχεδιασμός της —όπως η διάταξη των πυρήνων, ο τρόπος με τον οποίο μοιράζονται την προσωρινή μνήμη μεταξύ των πυρήνων και άλλοι σχετικοί παράγοντες— μπορούν να οδηγήσουν σε λιγότερο αποδοτική λειτουργία του χρονοπρογραμματιστή.
- Γι' αυτό η ύπαρξη επιλογών είναι ένα από τα σημαντικότερα πλεονεκτήματα του πλαισίου `sched-ext`, οπότε μη διστάσετε να δοκιμάσετε κάποιον και να δείτε ποιος λειτουργεί καλύτερα για τη δική σας περίπτωση χρήσης. `Παραδείγματα: σταθερότητα FPS, μέγιστες επιδόσεις, ανταπόκριση υπό εντατικούς φόρτους εργασίας κ.λπ.`

### Οι περιπτώσεις χρήσης αυτών των χρονοπρογραμματιστών μοιάζουν αρκετά... γιατί συμβαίνει αυτό;

Κυρίως επειδή είναι χρονοπρογραμματιστές πολλαπλών χρήσεων, πράγμα που σημαίνει ότι μπορούν να εξυπηρετήσουν ποικίλους φόρτους εργασίας, ακόμη κι αν δεν υπερέχουν σε κάθε τομέα.

- Για να διαπιστώσετε ποιος χρονοπρογραμματιστής σας ταιριάζει καλύτερα, δεν υπάρχει καλύτερη συμβουλή από το να το δοκιμάσετε μόνοι σας.

### Γιατί μου λείπει ένας χρονοπρογραμματιστής που αναφέρουν ή δοκιμάζουν κάποιοι χρήστες στον διακομιστή Discord του CachyOS;
Βεβαιωθείτε ότι χρησιμοποιείτε την έκδοση bleeding edge του πακέτου `scx-scheds`, με όνομα `scx-scheds-git`.

- Ένας από τους λόγους μπορεί να είναι ότι αυτός ο χρονοπρογραμματιστής είναι πολύ καινούργιος και δοκιμάζεται αυτή τη στιγμή από τους χρήστες, οπότε δεν έχει προστεθεί ακόμη στο πακέτο `scx-scheds-git`.

### Γιατί κατέρρευσε ξαφνικά ο χρονοπρογραμματιστής; Είναι ασταθής;

- *Θα μπορούσαν να υπάρχουν μερικοί λόγοι για τους οποίους συνέβη αυτό:*
  - Ένας από τους πιο συνηθισμένους λόγους είναι ότι χρησιμοποιούσατε το `ananicy-cpp` παράλληλα με τον χρονοπρογραμματιστή. Γι' αυτό προσθέσαμε αυτήν την [προειδοποίηση](/el/configuration/sched-ext#ananicy-cpp-και-sched-ext).
  - Ένας άλλος λόγος θα μπορούσε να είναι ότι ο φόρτος εργασίας που εκτελούσατε ξεπέρασε τα όρια και τη χωρητικότητα του χρονοπρογραμματιστή, προκαλώντας κόλλημα.
    - Παράδειγμα παράλογου φόρτου εργασίας: `hackbench`
  - Ή ο πιο προφανής λόγος: εντοπίσατε ένα σφάλμα στον χρονοπρογραμματιστή. Εάν ισχύει αυτό, παρακαλούμε αναφέρετέ το ως ζήτημα στο [GitHub](https://github.com/sched-ext/scx/issues) τους ή ενημερώστε
    τους σχετικά στο κανάλι `sched-ext` του Discord του CachyOS.

### Χρησιμοποιούσα προηγουμένως το scx_loader στο γραφικό περιβάλλον του Kernel Manager. Χρειάζεται να ακολουθήσω ακόμη τα βήματα μετάβασης;

- Σε αυτήν τη συγκεκριμένη περίπτωση, όχι, δεν είναι απαραίτητο, επειδή το Kernel Manager αναλαμβάνει ήδη τη διαδικασία μετάβασης.
  - *Εκτός εάν είχατε προσθέσει προηγουμένως προσαρμοσμένες παραμέτρους στο `/etc/default/scx` και θέλετε ακόμη να τις χρησιμοποιείτε.*
