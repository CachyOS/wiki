Extensible Scheduler Class（更为人熟知的名称是 `sched-ext`）是一个 Linux 内核功能，它允许使用
BPF（Berkeley Package Filter）实现内核线程调度器，并动态加载它们。本质上，这允许终端用户在用户空间更改他们的调度器，而无需
为了使用不同的调度器而构建另一个内核。

:::note
使用任何 sched-ext 调度器将暂时分离默认内核调度器。当 sched-ext 调度器停止时，默认内核调度器将重新接管。

示例：EEVDF 或 BORE。
:::

:::tip[在他们的 [Discord 服务器](https://discord.gg/b2J8DrWa7t) 上与开发者联系]
:::

- *调度器可以在 `scx-scheds` 和 `scx-scheds-git` 包中找到。*
  ```sh
  # 稳定分支 + scx_loader 和 scxctl 工具。
  sudo pacman -S scx-scheds scx-tools

  # 最新边缘分支（此分支包含来自 master 分支的最新更改。）+ scx_loader 和 scxctl 工具。
  sudo pacman -S scx-scheds-git scx-tools-git
  ```

  :::note
  `scx-scheds-git` 包可能不包含每个实验性调度器，因为有些是在尚未合并到 master 分支的单独功能分支中开发的。
  :::

## 如何启动和管理调度器

:::note
`scxctl` 和 `scx_loader` 都需要管理权限来启动/停止/切换调度器。

因此你需要使用 `sudo` 运行它们，或使用授予必要权限的 polkit agent。

不使用 `sudo` 时，scxctl/scx_loader 将通过 polkit agent 请求身份验证。
:::

<Tabs>

<TabItem label='终端'>

- *要启动调度器，打开终端并输入以下命令：*
  ```sh title='启动 rusty 的示例'
  sudo scx_rusty
  ```

*这将启动 rusty 调度器并分离默认调度器。*

要停止调度器。按 `CTRL + C`，调度器将被停止，默认内核调度器将重新接管。

</TabItem>

`scxctl` 是一个用于与 `scx_loader` 交互的 CLI DBUS 客户端。

- 功能：
  - 获取当前调度器和模式
  - 列出所有可用调度器
  - 以给定模式或使用给定参数启动调度器
  - 在调度器和模式之间切换
  - 停止运行的调度器
  - 重启运行的调度器

*顾名思义，它是一个使用 D-Bus 接口作为 sched-ext 框架的加载器和管理器的实用程序。*

    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.StartScheduler string:scx_rusty uint32:0
    ```
  - ```sh title='使用参数启动调度器'
    # 此示例使用以下标志启动 scx_bpfland：-k -c 0
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.StartSchedulerWithArgs string:scx_bpfland array:string:"-k","-c","0"
    ```
  - ```sh title='停止当前运行的调度器'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.StopScheduler
    ```
  - ```sh title='切换到默认调度器'
    # scx_loader 将切换到在 scx_loader 配置文件中设置的默认调度器
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.RestoreDefault
    ```
  - ```sh title='切换到模式 2 中的另一个调度器'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.SwitchScheduler string:scx_lavd uint32:2
    # 这切换到 scx_lavd，调度器模式 2 意味着它以省电模式启动 LAVD
    ```
  - ```sh title='使用参数切换到另一个调度器'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.scx.Loader.SwitchSchedulerWithArgs string:scx_bpfland array:string:"-k","-c","0"

    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.freedesktop.DBus.Properties.Get string:org.scx.Loader string:CurrentScheduler
    ```
  - ```sh title='获取支持的调度器列表'
    dbus-send --system --print-reply --dest=org.scx.Loader /org/scx/Loader org.freedesktop.DBus.Properties.Get string:org.scx.Loader string:SupportedSchedulers

### [scx_beerland](https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_beerland)

**开发者：Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

生产就绪？ <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

scx_beerland 是一个旨在优先考虑局部性和可扩展性的调度器。

优先将任务保留在同一 CPU 上以维持缓存局部性，同时通过在系统未饱和时使用本地 DSQs（每 CPU 运行队列）来确保跨多个 CPU 的良好可扩展性。

- 使用场景：
  - 缓存密集型工作负载
  - 拥有大量 CPU 的系统
  - 游戏：在某些游戏中表现出奇好的效果，但效果可能因人而异。
  - 服务器：由于其可扩展性和局部性优化，适用于通用服务器工作负载。
  - 也可用于桌面使用。

#### 调度器模式

目前没有。

### [scx_bpfland](<https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_bpfland>)

**开发者：Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

生产就绪？ <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

一个基于 vruntime 的 sched_ext 调度器，优先处理交互式工作负载。高度灵活且易于适应。

Bpfland 在决定使用哪些核心时，会考虑它们的缓存布局以及哪些核心共享相同的 L2/L3 缓存，从而导致更少的缓存未命中 = 更多性能。

- 使用场景：
  - 游戏
  - 桌面使用
  - 多媒体/音频制作
  - 在密集型工作负载下出色的交互性
  - 省电
  - 服务器

#### 调度器模式

##### 低延迟

* **命令行标志：** `-m performance -w`
* **说明：** 旨在以降低吞吐量为代价来降低延迟。适用于音频处理和多媒体等软实时应用程序。

##### 省电

* **命令行标志：** `-s 20000 -m powersave -I 100 -t 100`
* **说明：** 优先考虑电源效率。偏好性能较低的核心（例如 Intel 上的 E-cores）。

##### 服务器

* **命令行标志：** `-s 20000 -S`
* **说明：** 优先处理具有严格亲和性的任务。此选项可以增加吞吐量，但以增加延迟为代价，更适合服务器工作负载。

### [scx_cake](https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_cake)

**开发者：RitzDaCat (RitzDaCat [GitHub](<https://github.com/RitzDaCat>))**

- 生产就绪？ <Icon name="information" color="var(--sl-color-text-accent)" size="2rem" />

`scx_cake` 是一个实验性 BPF CPU 调度器，它将网络 [CAKE](https://www.bufferbloat.net/projects/codel/wiki/Cake/) 算法的 DRR++（Deficit Round Robin++）适配用于 CPU 调度。
- 4 级分类 — 任务按 EWMA avg_runtime 排序为 Critical / Interactive / Frame / Bulk
- 零全局原子操作 — 带 MESI 保护写入的每 CPU BSS 数组消除了总线锁定
- 内核委托的空闲选择 — scx_bpf_select_cpu_dfl() 用于权威、零陈旧性的 CPU 选择
- 每 LLC DSQ 分片 — 消除多 chiplet CPU 上的跨 CCD 锁争用
- DRR++ 赤字跟踪 — 网络 CAKE 的流公平算法适配用于 CPU 任务调度

专为现代 AMD 和 Intel 硬件上的游戏工作负载设计。

- 使用场景：
  - 游戏

#### 4 级系统

`scx_cake` 根据任务的 **EWMA**（指数加权移动平均）运行时间将每个任务分类为四个级别之一。分类是自动且连续的 — 任务的行为变化时会在级别之间移动。

##### 级别门限

| 级别   | 名称        | avg_runtime | 典型工作负载                                       | 时间片 | 饥饿限制 |
| :----- | :---------- | :---------- | :----------------------------------------------------- | :------ | :--------- |
| **T0** | Critical    | < 100µs     | IRQ 处理程序、输入驱动程序、音频（PipeWire）、网络 | 0.5ms   | 3ms        |
| **T1** | Interactive | < 2ms       | 合成器、游戏物理、游戏 AI、短任务      | 2.0ms   | 8ms        |
| **T2** | Frame       | < 8ms       | 游戏渲染线程、视频编码                    | 4.0ms   | 40ms       |
| **T3** | Bulk        | ≥ 8ms       | 编译、后台索引、批处理任务           | 8.0ms   | 100ms      |

:::tip
**没有游戏任务应该在 T3 中**。游戏渲染线程每帧运行 2-8ms → T2。物理/AI 运行 0.5-2ms → T1。输入处理程序运行 < 100µs → T0。只有执行 8ms+ 不间断 CPU 工作（着色器编译、加载屏幕）的任务才会进入 T3。
:::

##### 分类如何工作

1. **初始放置**：基于 `nice` 值 — `nice < 0` → T0，`nice 0-10` → T1，`nice > 10` → T3
2. **运行时权威**：大约 3 次停止后，EWMA avg_runtime 成为权威值。一个 nice -5 的任务如果运行 50ms 的突发，将重新分类为 T3，无论 nice 值如何。
3. **迟滞**：10% 的死区防止在级别边界处振荡。升级需要 avg_runtime 明显低于门限；降级是即时的。
4. **渐进退避**：一旦级别在 3+ 次连续停止后稳定，重新分类频率按级别下降：T0 每 1024 次停止重新检查，T3 每 16 次。不稳定性重置为全频率检查。

##### DRR++ 赤字跟踪

改编自网络 CAKE 的流公平性：

- 每个任务开始时有一个 **赤字**（时间片 + 新流奖励 ≈ 10ms 信用）
- 每次执行消耗与运行时间成比例的赤字
- 当赤字耗尽 → 新流奖励被移除 → 任务正常竞争
- 这为新创建的线程（游戏启动工作线程）提供了即时响应性，然后自然衰减

##### DVFS（CPU 频率缩放）

每个级别通过 RODATA 查找表映射到 CPU 性能目标：

| 级别  | 目标               | 理由                                             |
| :---- | :------------------- | :---------------------------------------------------- |
| T0-T2 | 100%（最大频率） | 游戏工作负载需要完整性能                |
| T3    | 75%                  | 后台工作可以稍微慢一点以节省电源 |

在 Intel 混合 CPU 上（`has_hybrid = true`），目标按每个核心的 `cpuperf_cap` 缩放，以防止在 E-cores 上过度请求频率。

#### 配置文件（`--profile, -p`）

| 配置文件     | 时间片 | 饥饿限制 | 使用场景                              |
| :---------- | :------ | :--------- | :------------------------------------ |
| **gaming**  | 2ms     | 100ms      | **（默认）** 为大多数游戏平衡 |
| **esports** | 1ms     | 50ms       | 竞技 FPS，超低延迟    |
| **legacy**  | 4ms     | 200ms      | 旧 CPU，省电            |
| **default** | 2ms     | 100ms      | gaming 的别名                      |

### [scx_cosmos](https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_cosmos)

**开发者：Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

- 生产就绪？ <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

轻量级调度器，针对保留任务到 CPU 的局部性进行了优化。

当系统未饱和时，调度器优先使用本地 DSQs 将任务保留在同一 CPU 上。这不仅保持了局部性，而且与共享 DSQs 相比减少了锁争用，从而实现了跨多个 CPU 的良好可扩展性。

- 使用场景：
  - 通用调度器：调度器应适应服务器工作负载或桌面工作负载。

#### 调度器模式

##### Auto

* **命令行标志：** 无。
* **说明：**

##### Gaming

* **命令行标志：** `-s 700 -S`
* **说明：** 通过减少共享 SMT 核心上的争用，牺牲吞吐量以提高游戏性能的一致性。

##### Power Save

* **命令行标志：** `-m powersave`
* **说明：** 优先考虑电源效率。偏好性能较低的核心（例如，Intel 上的 E-cores）。

##### Low Latency

* **命令行标志：** `-s 700 -S -m performance -w`
* **说明：** 旨在以降低吞吐量为代价来降低延迟。适用于音频处理和多媒体等软实时应用程序。在可用核心上提供更均匀的负载分布，牺牲效率。

##### Server

* **命令行标志：** `-s 20000 -c 75 -p 250`
* **说明：** 启用地址空间亲和性以提高某些缓存敏感工作负载的局部性和性能。切片持续时间设置为 20ms，轮询监控调度器多久比较一次 CPU 利用率与 CPU 繁忙阈值以决定系统何时繁忙。

### [scx_flash](<https://github.com/sched-ext/scx/tree/main/scheds/rust/scx_flash>)

**开发者：Andrea Righi (arighi [GitHub](<https://github.com/arighi>))**

生产就绪？ <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

一个专注于确保任务间公平性和性能可预测性的调度器。

它使用[最早截止时间优先（EDF）策略](https://www.geeksforgeeks.org/operating-systems/earliest-deadline-first-edf-cpu-scheduling-algorithm/)，其中每个任务被分配一个"延迟"权重。此权重根据任务在完整时间片用完之前释放 CPU 的频率动态调整。

提前释放 CPU 的任务被赋予更高的延迟权重，优先于完全消耗其时间片的任务。

- 使用场景：
  - 游戏
  - 延迟敏感的工作负载，如多媒体或实时音频处理
  - 在过载情况下需要响应性
  - 性能一致性
  - 服务器

#### 调度器模式

##### Low Latency

### [scx_flow](https://github.com/sched-ext/scx/tree/main/scheds/experimental/scx_flow)

**开发者：Galih Tama (galpt [GitHub](https://github.com/galpt))**

生产就绪？ <Icon name="approve-check" color="var(--sl-color-text-accent)" size="2rem" />

scx_flow 是一个基于预算的调度器，它根据任务剩余的预算将任务排序到四个 O(1) FIFO 级别之一。没有启发式方法，没有评分算法，没有自适应调优 — 每个决定都来自一个数字：*剩余预算*。

- 使用场景：
  - 通用桌面和工作站多任务处理
  - 打开后台应用程序时玩游戏
  - 运行构建、测试或容器时的开发工作
  - 混合负载下交互响应性重要的任何场景
  - 需要确定性、可解释调度的系统（嵌入式控制、机器人、航空电子）

#### 工作原理 — 预算

将每个任务视为具有"响应性预算"。当任务睡眠（等待某事）时，它会积累预算。当它唤醒并运行时，它会花费预算。唤醒时仍持有预算的任务是交互性的标志 — 它们会立即被调度到上次运行的 CPU，完全绕过级别系统。耗尽预算的任务会重新入队到四个 FIFO 级别之一。

##### 四个调度级别

当任务重新入队（不是唤醒）时，其剩余预算决定它进入哪个级别：

| 级别 | 预算阈值 | 什么类型的任务会到这里 |
|---|---|---|
| **Priority** | ≥ 1.5ms | 经常睡眠且短暂运行的交互式任务 |
| **Normal** | ≥ 1ms | 剩余预算充足的典型任务 |
| **Low** | ≥ 0.5ms | 预算不足的任务 |
| **Deficit** | < 0.5ms | 批量工作线程、CPU 占用大户、后台任务 |

每个级别都是一个普通的 FIFO 队列 — O(1) 入队，O(1) 出队。没有树遍历，没有优先级重新计算。

##### 无饥饿，无优先级反转

调度函数并不每次都先耗尽 Priority。它在每次调用时轮换起始级别 — `gen & 3` 决定从哪里开始。因此 Deficit 级别永远不会等待超过 3 个调度周期就会被优先服务。这意味着即使在高交互负载下，批量工作线程也会取得进展，并且没有优先级反转，因为没有单个级别可以独占 CPU。

##### 唤醒完全跳过队列

当任务唤醒（它正在睡眠，现在有事要做）时，它不会在任何级别队列中等待。它通过 `SCX_DSQ_LOCAL_ON` 直接进入上次运行的 CPU — 缓存预热且立即执行。这就是保持交互式任务灵敏的原因：睡眠的 Discord 或浏览器标签页唤醒时带有预算，并在微秒内被调度，而不是毫秒。

##### 固定任务始终优先

无法在 CPU 之间迁移的任务（setaffinity）拥有自己的每 CPU FIFO 队列，对任何级别都具有绝对优先级。它们在该 CPU 上运行级别系统中的任何内容之前被调度。

##### 结果

交互式任务（键盘输入、UI 更新、音频线程、网络轮询）几乎总是在唤醒时带有预算并获得快速通道。CPU 密集型批处理工作（编译、下载、后台索引）耗尽预算并进入 Deficit 级别，在那里由于轮换调度，它仍然取得进展。无需调优。

##### 无配置文件，无自动调优，无模式

scx_flow **没有** Gaming、Power Save 或 Low Latency 模式 — 与早期版本不同，它也没有自适应控制循环。轮换级别调度和预算阈值是编译时常量。你得到的是什么就运行什么：确定性、可解释性，并且在每个系统上相同。如果任务有预算，它就获得优先级。如果没有，它公平地共享 Deficit 级别。这就是整个策略。

#### Web UI

当 scx_flow 启动时，它会自动在 **[http://localhost:50005](http://localhost:50005)** 提供实时指标仪表板。在任何浏览器中打开它 — 无需额外标志。

仪表板显示：
- 每个级别经过了多少次调度（Priority / Normal / Low / Deficit）
- 系统信息：运行任务、正常运行时间、总调度计数
- 级别分布条，让你一眼看出是交互式还是批量工作占主导
- 每个指标卡片都可点击 — 打开带有迷你图和条形图的历史模态框
- 所有值通过轮询每秒更新 — 无需刷新页面

如果页面未加载，调度器可能已停止运行（内核回退到内置 EEVDF）。

```sh

sudo scx_flow --no-webui
```

当 `scx_loader` 与限制套接字族的 systemd 加固（`RestrictAddressFamilies`、`SocketBindDeny`）一起运行时，TCP 绑定被阻止，scx_flow 回退到 `/tmp/scx_flow.sock` 的 Unix 套接字。在这种情况下，浏览器无法直接访问仪表板 — 如果你不需要 UI，临时运行 `sudo scx_flow --no-webui` 以消除错误。

:::

### 使用 schbench 测试调度器延迟

schbench 是一个调度器基准测试，旨在测量模拟服务器风格工作负载下的调度器延迟。它生成可配置数量的 "worker" 和 "message" 线程，其中消息反复唤醒 worker。通过测量从唤醒到这些 worker 线程执行的延迟分布，它提供了有关内核处理线程唤醒、平衡和 CPU 争用能力的关键见解，特别是在负载下。

#### 使用场景

你可以使用 `schbench` 来：

- **评估调度器延迟：** 确定线程唤醒后多快被调度。
- **比较调度器之间的唤醒性能：** 检测上下文切换和唤醒延迟的改进或退化。
- **测试内核或调度器补丁的影响：** 评估调优或更新是否影响调度公平性和响应性。

#### 安装

`schbench` 在 CachyOS 仓库中可用：
```bash
sudo pacman -S schbench
```

#### 运行基准测试

运行 `schbench` 进行一般延迟测试的简单方法是：
```bash
schbench -m 2 -t 8 -r 60
```

此示例运行：
- 2 个消息线程（`-m 2`）
- 每个消息线程 8 个工作线程（`-t 8`）
- 总运行时间 60 秒（`-r 60`）

你可以根据 CPU 核心数和所需负载级别调整这些值。

以下是解释一些关键选项的表格：

| 选项                       | 说明                                                     |
| ---------------------------- | --------------------------------------------------------------- |
| `-C, --calibrate`            | 运行校准并报告时间（无基准测试）。               |
| `-L, --no-locking`           | 在 CPU 工作期间禁用自旋锁（默认：启用锁定）。   |
| `-m, --message-threads <n>`  | 消息线程数（默认：1）。                         |
| `-t, --threads <n>`          | 每个消息线程的工作线程数（默认：CPU 数量）。    |
| `-r, --runtime <sec>`        | 基准测试持续时间（默认：30）。                               |
| `-F, --cache_footprint <KB>` | 缓存占用大小（默认：256）。                            |
| `-n, --operations <count>`   | 要执行的 "think time" 操作数（默认：5）。      |
| `-A, --auto-rps`             | 自动增加 RPS 直到达到 CPU 利用率目标。 |
| `-R, --rps <count>`          | 每秒请求模式。                                       |
| `-p, --pipe <bytes>`         | 模拟管道传输测试。                                  |
| `-w, --warmuptime <sec>`     | 收集统计信息前的预热持续时间（默认：0）。          |
| `-i, --intervaltime <sec>`   | 打印延迟的间隔（默认：10）。                  |
| `-z, --zerotime <sec>`       | 清零延迟统计的间隔（默认：从不）。            |

##### 如何解释结果

- **Wakeup Latencies：**
  - 测量线程在收到信号后多快唤醒。
    - 这里的较低值（尤其是 **99th percentile**）意味着调度器更响应。
- **Request Latencies：**
  - 表示完成线程之间请求所需的时间。
    - 较低的延迟表示更好的线程间通信和调度效率。
- **RPS（Requests Per Second）：**
  - 显示持续吞吐量：
    - 较高的 **average RPS** 表示调度器在给定的配置下每秒可以处理更多工作。

总之：
- **好的调度器**将显示**低的唤醒和请求延迟**以及**一致的 RPS**。
- **效率较低的调度器**可能会表现出**高延迟峰值**或**不稳定的 RPS 值**。

:::note
这些结果可能因 CPU、核心数、系统负载以及调度器是否能够高效处理你的 CPU 架构而异。
:::

### 游戏基准测试建议

如果你想基准测试游戏以比较不同调度器的性能，以下是一些获得最准确结果的提示：

- **使用内置基准测试：** 许多现代游戏都带有内置基准测试工具。这些工具旨在通过每次运行相同的事件序列来提供一致的结果。
  - 查看此 [网站](https://www.pcgamingwiki.com/wiki/List_of_games_with_built-in_benchmarks) 获取包含内置基准测试的游戏列表。
- **一致的设置：** 确保每次测试运行的游戏设置（分辨率、图形质量等）相同。
- **关闭后台应用程序：** 后台运行的其他应用程序会影响性能。关闭不必要的程序以最小化其影响。
- 如果你没有使用内置基准测试，请尝试在每次测试运行中执行相同的操作。这可能包括遵循相同的路径、参与类似的战斗场景或执行相同的任务。
  - 即使瞄准的位置不同也可能导致不同的性能结果。
- **多次运行：** 执行多次基准测试运行并取平均值以考虑可变性。
- **使用性能监控工具：** 像 MangoHud 或 GOverlay 这样的工具可以提供实时性能指标，如 FPS、帧时间和 CPU/GPU 使用情况。
- **利用键盘快捷键或宏：**
  - 一个示例是创建一个键绑定，你可以在游戏中实时在不同调度器之间切换或更改它们的模式。
    - 这可以使用像 [scxctl](/zh/configuration/sched-ext#how-to-launch-and-manage-the-scheduler) 这样的工具完成，或通过创建更改活动调度器及其模式的自定义脚本来完成。

## scx_loader 配置

### 将调度器设置为默认（启动时）

要设置调度器在 `scx_loader` 启动时自动启动（例如，在启动时），请按照以下步骤操作：

<Steps>
1. **将示例配置文件** 复制到配置目录：
   ```sh
   sudo mkdir -p /etc/scx_loader
   sudo cp /usr/share/scx_loader/config.toml /etc/scx_loader/config.toml
   ```

2. **使用你喜欢的编辑器编辑配置文件**：
   ```sh
   sudo nano /etc/scx_loader/config.toml
   ```

3. **设置默认调度器和模式**。例如，设置 `scx_pandemonium` 为 `Auto` 模式：
   ```toml
   # This field specifies the scheduler that will be started automatically when scx_loader starts (e.g., on boot).
   default_sched = "scx_pandemonium"

   # This field specifies the mode which will be used when scx_loader starts (e.g., on boot).
   default_mode = "Auto"
   ```

4. **启用并启动服务**：
   ```sh
   sudo systemctl enable --now scx_loader.service
   ```
</Steps>

#### 配置查找顺序

`scx_loader` 按以下顺序搜索配置文件：

1. `/etc/scx_loader/config.toml`（首选）
2. `/etc/scx_loader.toml`
3. `/usr/share/scx_loader/config.toml`（默认模板）
4. `/usr/share/scx_loader.toml`

### 自定义调度器参数

你可以通过在配置文件中添加 `[scheds.scx_name]` 部分来自定义传递给每个调度器的不同模式的参数。

有关如何配置每个调度器参数的详细信息和示例，请参阅 [scx_loader 配置文档](https://github.com/sched-ext/scx-loader/blob/main/crates/scx_loader/configuration.md)。

## 从 scx.service 过渡到 scx_loader：综合指南

:::caution
不要尝试将 scx_loader.service 与 scx.service 一起运行，否则加载器服务将启动但什么都不做。

此冲突是因为两个服务都不知道对方，特别是关于哪个服务管理调度器。
:::

:::tip
CachyOS Kernel Manager 已经包含 [用于管理 scx_loader 的 GUI。](/zh/features/kernel_manager#sched-ext-framework-management)
:::

首先让我们从 scx.service 文件结构与 scx_loader 配置文件结构的近距离比较开始。

*如果你之前像下面的示例一样使用旧的 scx.service 运行 LAVD：*

```sh title='scx.service 文件结构'
# List of scx_schedulers: scx_bpfland scx_central scx_flash scx_lavd scx_layered scx_nest scx_qmap scx_rlfifo scx_rustland scx_rusty scx_simple scx_userland
SCX_SCHEDULER=scx_lavd

# Set custom flags for the scheduler
SCX_FLAGS='--performance'
```

那么 scx_loader 配置文件中的等价物将如下所示：

```sh title='scx_loader 文件结构'
default_sched = "scx_lavd"
default_mode = "Auto"

[scheds.scx_lavd]
auto_mode = ["--performance"]
```

[有关如何配置 scx_loader 文件的更多信息](https://github.com/sched-ext/scx-loader/blob/main/crates/scx_loader/configuration.md#scx_loader-configuration-file)

  按照下面的指南轻松从 `scx systemd service` 过渡到新的 `scx_loader` 实用程序。
  <Steps>
  1. ```sh title='禁用 scx.service 以支持 scx_loader.service'
      systemctl disable --now scx.service && systemctl enable --now scx_loader.service
      ```
  2. ```sh title='为 scx_loader 创建配置文件并添加默认结构'
     # Micro 编辑器将创建一个新文件。
     sudo micro /etc/scx_loader.toml
     # 添加以下行：

     default_sched = "scx_bpfland" # 编辑此行为你希望 scx_loader 在启动时启动的调度器
     default_mode = "Auto" # 可能的值："Auto"、"Gaming"、"LowLatency"、"PowerSave"。

     # 按 CTRL + S 保存更改，按 CTRL + Q 退出 Micro。
     ```
  3. ```sh title='重启 scx_loader'
     systemctl restart scx_loader.service
     ```

## FAQ

### 选项太多了...为什么不只做一个擅长一切的调度器？

主要原因是 CPU 调度没有一刀切的解决方案。不同的工作负载有不同的需求和优先级，针对一种类型的工作负载优化的调度器可能不适合另一种工作负载。

你可以将 CPU 调度器视为不同的鞋子，每双都针对特定活动设计。例如，在针对服务器工作负载优化的调度器上运行游戏可能会导致次优性能和增加的延迟，而在服务器上为游戏设计的调度器可能导致资源利用率低和吞吐量降低。

这就是 sched-ext 的魔力。限制不再是问题。

### 为什么 X 调度器比其他调度器表现差？

- 比较它们时要考虑许多变量。例如，它们如何测量任务的权重？它们是否优先处理交互式任务而不是非交互式任务？
  最终，这取决于它们的设计选择。

### 为什么每个人都一直说这个 X 调度器是 X 案例的最佳选择，但它对我的表现并不好？

- 与上一个答案一样，CPU 的选择及其设计，如核心布局、它们如何在核心之间共享缓存以及其他相关因素，可能导致调度器效率较低。
- 这就是为什么拥有选择是 sched-ext 框架的亮点之一，所以不要害怕尝试一个，看看哪个最适合你的使用场景。`示例：fps 稳定性、最大性能、密集型工作负载下的响应性等。`

### 这些调度器的使用场景非常相似...为什么？

主要是因为它们是多功能调度器，这意味着它们可以容纳各种工作负载，即使它们可能不会在每个领域都表现出色。

- 要确定哪个调度器最适合你，没有比亲自尝试更好的建议了。

### 为什么我缺少一些用户在 CachyOS Discord 服务器中提到或测试的调度器？
确保你使用的是名为 `scx-scheds-git` 的 scx-scheds 包的最新边缘版本

- 原因之一是这个调度器非常新，目前正在由用户测试，因此尚未添加到 `scx-scheds-git` 包中。

### 为什么调度器突然崩溃了？它不稳定吗？

- *可能有几个原因导致这种情况：*
  - 最常见的原因之一是你与调度器一起使用了 ananicy-cpp。这就是我们添加此 [警告](/zh/configuration/sched-ext#ananicy-cpp--sched-ext) 的原因
  - 另一个原因可能是你运行的工作负载超出了调度器的限制和容量，导致其停滞。
    - 不合理工作负载的示例：`hackbench`
  - 或者更明显的原因，你在调度器中发现了一个 bug，如果是这样。请在他们的 [GitHub](https://github.com/sched-ext/scx/issues) 中报告问题，或让他们知道
    在 CachyOS Discord 频道 `sched-ext` 中

### 我之前在 Kernel Manager GUI 中使用过 scx_loader。我还需要遵循过渡步骤吗？

- 在这种情况下，不需要，因为 Kernel Manager 已经处理了过渡过程。
  - *除非你之前在 `/etc/default/scx` 中添加了自定义标志，并且仍想使用它们。*
