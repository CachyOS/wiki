## Предварителна настройка

### Мениджър за зареждане GRUB

Ако използвате GRUB, изпълнете следната команда, за да активирате поддръжката на Secure Boot в GRUB чрез CA ключове.

```bash
sudo grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=cachyos --modules="tpm" --disable-shim-lock
```

:::note
Зареждането на ненужни модули във вашия мениджър за зареждане крие потенциален риск за сигурността.
Изпълнете тази команда само ако действително имате нужда от Secure Boot.
:::

### Активиране на Setup Mode в UEFI

Първо трябва да влезете в настройките на фърмуера и да зададете режима на Secure Boot на "Setup Mode". Можете да рестартирате от вече работеща система директно в настройките на фърмуера със следната команда:

```bash
systemctl reboot --firmware-setup
```

<br />
<ImageComponent imgsrc={import('~/assets/images/ideapad-bios-secure-boot.jpg')} />

Така изглежда BIOS на Lenovo Ideapad 5 Pro. Нулирайте в режим на настройка (Reset to setup mode) или възстановете фабричните ключове и рестартирайте обратно в системата.

#### Автоматично нулиране

На някои дънни платки Gigabyte след "reset to setup mode" веднага се появява диалогов прозорец "reset without saving"
<ImageComponent imgsrc={import('~/assets/images/gigabyte-reset-without-saving.jpg')} />
който трябва да отхвърлите, тъй като в противен случай системата ще се рестартира и ще деактивира Setup Mode.

Вместо това заредете директно операционната система (Save & Exit и изберете вашия мениджър за зареждане в Boot Override).

#### Липса на Setup Mode

Някои дънни платки на MSI и ASUS нямат опция Setup Mode.

##### MSI

Задайте Secure Boot Mode на "custom" и изберете опцията за съвместимост "maximum security" (това е важно: при настройката по подразбиране може да не успеете да заредите CachyOS от вашия мениджър за зареждане!). След това влезте в "key management" и следвайте двете стъпки, показани на изображението по-долу:
<br />
<ImageComponent imgsrc={import('~/assets/images/MSI-bios-secure-boot.jpg')} />

##### ASUS

Навигирайте до Boot → Secure Boot, задайте Secure Boot Mode на Custom, след това отворете Key Management и изберете "Delete all Secure Boot Variables".

#### Инсталиране на sbctl и записване на ключовете

Преди да продължите, уверете се дали `sbctl` е инсталиран.

[sbctl](https://github.com/Foxboron/sbctl) е удобен за потребителя мениджър на ключове за Secure Boot, който може да настройва Secure Boot, да управлява ключове и да следи файловете, които трябва да бъдат подписани във веригата на зареждане.

<details>
    <summary>Как да инсталирате sbctl</summary>
    ```bash title='Отворете терминал и изпълнете следната команда'
    sudo pacman -S sbctl
    ```
</details>

След като `sbctl` е инсталиран, трябва да го настроите и да запишете ключовете си във фърмуера. Процесът е доста лесен — просто следвайте стъпките по-долу.

<Steps>
1. Проверете дали Setup Mode е активиран:
    ```bash
    sudo sbctl status
    ```
    <details>
        <summary>Очакван изход</summary>
        ```bash
        Installed:      ✘ sbctl is not installed
        Setup Mode:     ✘ Enabled
        Secure Boot     ✘ Disabled
        ```
    </details>
2. Създайте свои собствени ключове за Secure Boot:
    ```bash
    sudo sbctl create-keys
    ```
    <details>
        <summary>Пример за успешно създаване на ключове</summary>
        ```bash
        Created Owner UUID a9fbbdb7-a05f-48d5-b63a-08c5df45ee70
        Creating secure boot keys...✔
        Secure boot keys created!
        ```
    </details>
3. Запишете вашите ключове заедно с тези на Microsoft и вградените ключове на OEM фърмуера:
    ```bash
    sudo sbctl enroll-keys --microsoft --firmware-builtin
    ```
    <details>
        <summary>Очакван изход</summary>
        ```bash
        Enrolling keys to EFI variables...✔
        Enrolled keys to the EFI variables!
        ```
    </details>

    :::caution[Дънни платки ASUS / Gigabyte — Не използвайте `--firmware-builtin`]
    При някои дънни платки ASUS и Gigabyte използването на флага `--firmware-builtin` води до дублирани записи
    в EFI променливите за ключове (напр. `builtin-db` се появява няколко пъти във `Vendor Keys`).
    Когато след това активирате Secure Boot в настройките на UEFI, дънната платка засича тази
    непоследователна структура на ключовете и извежда грешка **Secure Boot Violation**, преди мениджърът
    за зареждане да успее да стартира.

    Използвайте само `--microsoft` при дънни платки ASUS / Gigabyte:

    ```bash
    sudo sbctl enroll-keys --microsoft
    ```

    Ако `Vendor Keys` показва `microsoft builtin-db builtin-db ...`, ключовете трябва да бъдат
    записани наново. Влезте отново в Setup Mode в UEFI (като изтриете всички ключове), след което
    изпълнете отново `sbctl enroll-keys --microsoft` без `--firmware-builtin`.
    :::


4. Проверете отново състоянието на sbctl, за да се уверите, че ключовете са записани и Setup Mode е деактивиран:
    ```bash
    sudo sbctl status
    ```
    <details>
        <summary>Очакван изход</summary>
        ```bash
        Installed:      ✔ sbctl is installed
        Owner GUID:     a9fbbdb7-a05f-48d5-b63a-08c5df45ee70
        Setup Mode:     ✔ Disabled
        Secure Boot     ✘ Disabled
        Vendor Keys:    microsoft
        ```
    </details>

    :::note[Setup Mode все още показва Enabled?]
    Ако `Setup Mode` показва **Enabled**, влезте в настройките на фърмуера и **временно деактивирайте Secure Boot**.
    Заредете обратно в системата, проверете отново състоянието на sbctl, продължете с [Подписване на образа на ядрото и мениджъра за зареждане](#подписване-на-образа-на-ядрото-и-мениджъра-за-зареждане)
    по-долу, след което рестартирайте и активирайте отново Secure Boot в настройките на фърмуера.
    :::
    
</Steps>

## Подписване на образа на ядрото и мениджъра за зареждане

<Tabs syncKey="boot-manager">
<TabItem label='Limine'>
Limine е специален мениджър за зареждане, който позволява проверка на хеша на образите на ядрото
и други файлове, използвани от Limine по време на зареждане. Ако това е активирано, всякаква
ръчна намеса от страна на потребителя, напр. подписване на образа чрез `sbctl-batch-sign`, ще
промени хеша на съответните файлове и проверката на контролната сума на Limine ще се провали.

Въпреки това подписването на тези файлове не е необходимо при Limine, тъй като той има специален
процес на зареждане, който заобикаля EFI верижното зареждане и проверките на подписите. Единствените EFI
двоични файлове, които трябва да бъдат подписани, са самите файлове на Limine.

:::caution[Limine >= 11.2.0]
Започвайки от Limine 11.2.0, политиките за Secure Boot се **прилагат стриктно**, когато UEFI Secure Boot е активен:

- Контролната сума BLAKE2B на конфигурацията **трябва** да бъде записана в EFI двоичния файл на Limine, в противен случай Limine ще спре с паника: `SECURE BOOT IS ACTIVE BUT NO CONFIG CHECKSUM IS ENROLLED`
- Всички файлови пътища в `limine.conf` (ядро, initramfs и др.) **трябва** да имат добавени BLAKE2B хешове (напр. `boot():/vmlinuz-linux#<hash>`)
- Редакторът на конфигурацията е безусловно деактивиран
- Несъответствията в хешовете винаги водят до паника
:::

За да активирате автоматичното записване на контролната сума на конфигурацията, задайте следното в `/etc/default/limine`:

```sh
ENABLE_ENROLL_LIMINE_CONFIG=yes
```

Продължете с генерирането на хеш за началното изображение (splash image) на Limine:

:::note[За изпълнението на следните стъпки са необходими root права — уверете се, че използвате sudo или сте преминали към потребителя root, преди да продължите.]
:::

<Steps>

1. Проверете текущото име и път до началното изображение в конфигурационния файл:
    ```sh title="Отворете терминал и изпълнете следната команда:"
    sudo cat /boot/limine.conf
    ```
    Трябва да видите ред като този:
    ```sh
    wallpaper: boot():/limine-splash.png
    ```
2. Генерирайте BLAKE2B хеш за началното изображение и го добавете към пътя в конфигурационния файл:
    ```sh title="Изпълнете следната команда, като замените пътя с този, който открихте в предишната стъпка:"
    sudo b2sum /boot/limine-splash.png
    ```
    Това ще изведе хеш подобен на следния пример:
    ```sh
    75205d08fa9c61599897857e861d6b2f6da25465183fc4cc9efecffb22ee630efb510f2ef1b17677db94c28d5c69ad2ceb4d3892f5bec9cfa65c97b5ba16f52f
    ```
3. След като копирате новогенерирания хеш от предишната стъпка, отворете конфигурационния файл с текстов редактор и добавете хеша към пътя на началното изображение по следния начин:
    :::note[Не използвайте примерния хеш от по-горе — уверете се, че използвате този, който генерирахте в предишната стъпка.]
    :::
    ```sh
    wallpaper: boot():/limine-splash.png#75205d08fa9c61599897857e861d6b2f6da25465183fc4cc9efecffb22ee630efb510f2ef1b17677db94c28d5c69ad2ceb4d3892f5bec9cfa65c97b5ba16f52f
    ```
    Както виждате, хешът се добавя към пътя със символа `#`. Запазете файла, след като направите промяната.

</Steps>

След като активирате записването на контролната сума на конфигурацията и генерирате хеша за началното изображение, изпълнете следните команди, за да запишете контролната сума на конфигурацията и да подпишете EFI двоичния файл на Limine:

```sh
# Използвайте limine-enroll-config, за да запишете контролната сума на конфигурацията и да подпишете EFI двоичния файл на Limine
# Това използва sbctl под капака
sudo limine-enroll-config
sudo limine-update
```
</TabItem>
<TabItem label='systemd-boot'>

CachyOS предоставя [sbctl-batch-sign](https://github.com/CachyOS/CachyOS-Settings/blob/master/usr/bin/sbctl-batch-sign) —
скрипт, който взема списъка с файлове за подписване от `sudo sbctl verify` и ги подписва всички.

:::caution
При системи с отделни дялове `/boot` и `/boot/efi`, `sbctl` може да сканира за EFI двоични файлове само в `/boot/efi`.
Това води до неразпознаване на образите на ядрото, които се намират в `/boot`. `sbctl-batch-sign` заобикаля този проблем, като **винаги** сканира
`/boot` за файлове `vmlinuz-*`.
:::

```bash
sudo sbctl verify
Verifying file database and EFI images in /boot...
✘ /boot/1c4b5246eef05ac3bc87339323cd5101/6.10.0-cn4.0.fc40.x86_64/linux is not signed
✘ /boot/EFI/BOOT/BOOTX64.EFI is not signed
✘ /boot/EFI/systemd/systemd-bootx64.efi is not signed
✘ /boot/1c4b5246eef05ac3bc87339323cd5101/0-rescue/linux is not signed
✘ /boot/1c4b5246eef05ac3bc87339323cd5101/6.10.0-cn3.0.fc40.x86_64/linux is not signed

sudo sbctl-batch-sign

sudo sbctl verify
Verifying file database and EFI images in /boot...
✔ /boot/1c4b5246eef05ac3bc87339323cd5101/6.10.0-cn4.0.fc40.x86_64/linux is signed
✔ /boot/EFI/BOOT/BOOTX64.EFI is signed
✔ /boot/EFI/systemd/systemd-bootx64.efi is signed
✔ /boot/1c4b5246eef05ac3bc87339323cd5101/0-rescue/linux is signed
✔ /boot/1c4b5246eef05ac3bc87339323cd5101/6.10.0-cn3.0.fc40.x86_64/linux is signed
```

След като всички файлове са подписани, **рестартирайте системата и влезте в настройките на UEFI, за да активирате Secure Boot.**

:::caution[Дънни платки ASUS — активиране на Secure Boot]
Някои дънни платки ASUS се държат по различен начин от други производители при активиране на Secure Boot:

- **Използвайте `Windows UEFI Mode`, а не `Other OS`:**
  Името е подвеждащо — тази настройка просто определя дали Secure Boot се прилага.
  Задаването на `OS Type` на `Other OS` **активно деактивира** Secure Boot при дънните платки ASUS,
  независимо от всякакви други настройки. `sbctl status` ще продължи да показва
  `Secure Boot: Disabled` дори след рестартиране.

- **Няма отделен превключвател за включване/изключване на Secure Boot** при някои дънни платки ASUS.
  Secure Boot се активира косвено чрез избиране на `Windows UEFI Mode`.

Правилната конфигурация на ASUS BIOS за активиране на Secure Boot в този случай е:
```
Boot → Secure Boot
  OS Type          → Windows UEFI Mode
  Secure Boot Mode → Custom
```
:::

Вижте [тази секция за справка](/bg/configuration/secure_boot_setup#активиране-на-setup-mode-в-uefi)

Имайте предвид, че това е еднократен процес, тъй като подписването на файлове с флага `-s` ги запазва в базата данни на `sbctl`.

:::tip[Напомняне]
`sbctl` включва [pacman hook](https://wiki.archlinux.org/title/Pacman_hook), което означава, че автоматично ще
подписва всички нови файлове при актуализация на ядрото или мениджъра за зареждане.
:::

CachyOS използва `systemd-boot-update.service`, предоставена от systemd, за да обновява мениджъра за зареждане при рестартиране. Това означава, че `sbctl`
pacman hook **няма** да подпише обновените EFI двоични файлове. Като заобиколно решение можем да подпишем мениджъра за зареждане директно:

```sh
sudo sbctl sign -s -o /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed /usr/lib/systemd/boot/efi/systemd-bootx64.efi
```

:::note
Пропуснете тази стъпка, ако използвате [настройката за Easy Anti-Cheat](/bg/configuration/easy_anti_cheat). Там `systemd-boot-cachyos-signed`
предоставя systemd-boot, подписан от CachyOS.
:::
</TabItem>
<TabItem label='rEFInd'>

rEFInd стартира ядрата чрез фърмуера, така че фърмуерът проверява подписите на rEFInd и на всяко
ядро. Тези стъпки са за инсталации, при които EFI системният дял е монтиран в `/boot`, което е начинът, по който
инсталаторът на CachyOS настройва rEFInd. `bootctl --print-esp-path` трябва да изведе `/boot`.

Подпишете rEFInd и вашите ядра. Командата `find` пропуска ядрото за
[Easy Anti-Cheat](/bg/configuration/easy_anti_cheat), което вече е подписано от CachyOS:

```bash
sudo sbctl sign -s /boot/EFI/refind/refind_x64.efi
sudo find /boot -maxdepth 1 -name 'vmlinuz-*' ! -name vmlinuz-linux-cachyos-eac -exec sbctl sign -s {} \;
sudo sbctl verify
```

`sbctl verify` трябва да изведе rEFInd и всяко от вашите ядра като подписани. Ако използвате Easy Anti-Cheat, ще покаже също, че
`vmlinuz-linux-cachyos-eac` и `EFI/cachyos-eac/systemd-bootx64.efi` не са подписани. Това е очаквано — те са
подписани от CachyOS. **Не ги подписвайте**, в противен случай EAC повече няма да ги приема. След това **рестартирайте в настройките на UEFI
и активирайте Secure Boot.** При дънни платки ASUS вижте бележките в раздела systemd-boot.

Флагът `-s` запазва файловете в базата данни на `sbctl`, а неговият pacman hook подписва ядрата отново след актуализации.
pacman не обновява rEFInd на EFI системния дял. Ако сами стартирате `refind-install`, подпишете го отново
след това:

```bash
sudo sbctl sign-all
```

## Проверка на състоянието на Secure Boot

За да проверите дали Secure Boot действително е активиран, можете да изпълните една от следните команди:

```bash
sudo sbctl status
Installed:      ✓ sbctl is installed
Owner GUID:     a9fbbdb7-a05f-48d5-b63a-08c5df45ee70
Setup Mode:     ✓ Disabled
Secure Boot:    ✓ Enabled
Vendor Keys:    microsoft

bootctl
System:
      Firmware: UEFI 2.80 (INSYDE Corp. 28724.16435)
 Firmware Arch: x64
   Secure Boot: enabled (user)
  TPM2 Support: yes
  Measured UKI: no
  Boot into FW: supported
```

## Fwupd

За да използвате `fwupd` с активиран Secure Boot, подпишете изпълнимия UEFI файл:

```sh
sudo sbctl sign -s -o /usr/lib/fwupd/efi/fwupdx64.efi.signed /usr/lib/fwupd/efi/fwupdx64.efi
```

И добавете следното в `/etc/fwupd/fwupd.conf`:

```sh
[uefi_capsule]
DisableShimForSecureBoot=true
```
