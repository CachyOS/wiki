[Easy Anti-Cheat Linux v2](https://onlineservices.epicgames.com/news/introducing-easy-anti-cheat-linux-v2)
only lets games start when it can verify how the system was booted. It checks that:

- Secure Boot is enabled and the kernel is signed with a key that Epic trusts
- the system has a TPM 2.0, which records every step of the boot (measured boot)
- the kernel runs in lockdown integrity mode and only loads signed modules
- the IOMMU is enabled, kexec is disabled and the BPF LSM is active

CachyOS provides a dedicated kernel, `linux-cachyos-eac`, that meets these requirements, and a systemd-boot
signed with the same key. You keep your own Secure Boot keys. The only addition is the **CachyOS EAC CA**
certificate in the Secure Boot database, so that your firmware accepts the CachyOS-signed files.

The EAC kernel gets its own boot entry. Your normal boot entries stay unchanged, so you only boot into the
EAC entry when you want to play a game that uses EAC.

EAC requires a boot manager that verifies everything it loads against the Secure Boot database and
measures it into the TPM. systemd-boot does this, Limine does not. rEFInd does, but it is signed with your own
key, which EAC does not accept, and the same applies to GRUB. Limine, rEFInd and GRUB users therefore keep
their boot manager as the default and start the EAC kernel through the CachyOS-signed systemd-boot, which gets
its own firmware boot entry and is only used for the EAC boot.

The [`eac-setup` script](#setup-with-eac-setup) does the setup for you. The [manual setup](#manual-setup)
describes the same steps by hand.

## Requirements

- CachyOS installed in UEFI mode with **systemd-boot**, **Limine** or **rEFInd** as boot manager. With rEFInd,
  the EFI system partition has to be mounted at `/boot`, as the CachyOS installer sets it up. **GRUB** is
  supported experimentally, see [GRUB (experimental)](#grub-experimental).
- An up-to-date system (`sudo pacman -Syu`). `eac-setup` needs `cachyos-settings` 1.4.4 or newer, `eac-status`
  and the EAC support in `sbctl-batch-sign` need 1.4.2 or newer.
- **TPM 2.0** enabled in the firmware settings. A firmware TPM (AMD fTPM, Intel PTT) is fine.
- **IOMMU** enabled in the firmware settings (AMD-Vi / "IOMMU" on AMD, VT-d on Intel).
- NVIDIA GPUs: Maxwell or newer (GTX 750, GTX 900 series and later). The EAC kernel ships the NVIDIA modules as
  packages: `linux-cachyos-eac-nvidia-open` for Turing and newer (GTX 16 / RTX 20 series and later),
  `linux-cachyos-eac-nvidia-580xx` for Maxwell, Pascal and Volta.

:::caution[No DKMS modules]
The EAC kernel only loads modules that were signed when the kernel was built. NVIDIA, ZFS and Realtek r8125
modules are shipped as `linux-cachyos-eac-*` packages, other modules built with DKMS (for example
`virtualbox-host-dkms`) will not load in the EAC boot entry. Do not install `linux-cachyos-eac-headers`.
:::

:::danger[BitLocker and TPM disk unlock]
This setup changes the Secure Boot keys, which changes what the TPM measures. BitLocker on a Windows dual boot can
then ask for its recovery key, and a LUKS disk that you bound to the TPM yourself asks for its passphrase. Make sure
you have them before you start, otherwise you can lose access to your data.
:::

## Setup with eac-setup

`eac-setup` from `cachyos-settings` does the setup for systemd-boot, Limine, rEFInd and GRUB. It checks what is
already done, so you can run it again at any time, for example to repair the setup. Only the changes in the
firmware settings are left to you.

<Steps>

1. **Put the firmware into Setup Mode**

    Skip this step if you already use Secure Boot with keys created by `sbctl`, for example from the
    [Secure Boot guide](/configuration/secure_boot_setup). `eac-setup` then adds the CachyOS EAC CA to the
    Secure Boot database while Secure Boot stays enabled.

    Otherwise follow [Enabling Setup Mode in UEFI](/configuration/secure_boot_setup#enabling-setup-mode-in-uefi)
    and keep Secure Boot **disabled** for now.

    ```bash
    systemctl reboot --firmware-setup
    ```

2. **Run eac-setup**

    ```bash
    sudo eac-setup
    ```

    The script asks before it enrolls the Secure Boot keys, and pacman asks before it installs the packages.
    It runs these steps:

    - It checks the TPM, the IOMMU and which boot manager you use.
    - It enrolls the CachyOS EAC CA. In Setup Mode, it creates your own keys first and enrolls them together
      with Microsoft's keys.
    - It installs `linux-cachyos-eac`, `systemd-boot-cachyos-signed` and the `linux-cachyos-eac-*` module
      packages that match your system (NVIDIA, ZFS, r8125).
    - It signs your normal kernels with your own key, and Limine, rEFInd or GRUB as well, so your normal boot
      keeps working with Secure Boot enabled.
    - It keeps `sbctl` away from the CachyOS-signed files and restores their signatures if `sbctl` signed
      them again.
    - It creates the EAC boot entry from the kernel options of your running system plus the EAC options.
      With Limine, rEFInd and GRUB, it also installs the CachyOS-signed systemd-boot with its own
      "CachyOS EAC" firmware boot entry.

    If the firmware is not in Setup Mode and your keys were not created with `sbctl`, the script stops and
    asks you to put the firmware into Setup Mode. Do that and run it again.

    The EAC entry uses the kernel options that your system was booted with. If you change the kernel options
    of your normal boot entry later, reboot and run `sudo eac-setup` again.

3. **Enable Secure Boot**

    `eac-setup` tells you at the end if Secure Boot is still disabled. If it is already enabled, skip this
    step.

    Reboot into the firmware settings and enable Secure Boot. See the ASUS notes in the
    [Secure Boot guide](/configuration/secure_boot_setup#signing-the-kernel-image-and-boot-manager) if your board has no
    Secure Boot switch.

    ```bash
    systemctl reboot --firmware-setup
    ```

4. **Boot into EAC**

    ```bash
    sudo eac-setup boot
    ```

    This reboots into the EAC entry once. The reboot after your gaming session starts your normal system
    again. With systemd-boot, you can also select **CachyOS (EAC)** in the boot menu.

    :::caution
    The Limine and GRUB menus also show an entry for `linux-cachyos-eac`. Booting it through Limine or GRUB
    does **not** pass the EAC checks. Always use `sudo eac-setup boot`.
    :::

    Then check the result as described in [Verifying the setup](#verifying-the-setup).

</Steps>

### GRUB (experimental)

GRUB support is new and only tested in a virtual machine so far. It needs `cachyos-settings` 1.4.5 or newer.
Please report problems in the [CachyOS-Settings issue tracker](https://github.com/CachyOS/CachyOS-Settings/issues).

GRUB is set up with `eac-setup` only, there is no manual guide for it. The steps are the same as above. In
addition, the script makes these changes:

- It reinstalls GRUB with the `tpm` module and without the shim lock, and signs it with your own key.
  Without this, GRUB does not start your normal kernels with Secure Boot enabled.
- It copies the EAC kernel and its initramfs to the EFI system partition, because systemd-boot cannot read
  them from `/boot` on the root filesystem. They need about 40 MiB there. The script installs
  `cachyos-eac-grub-hook`, whose mkinitcpio hook updates the copy whenever the EAC kernel or its initramfs
  changes.
- It regenerates the GRUB menu. The menu then has a **CachyOS EAC (EFI BootNext)** entry under the UEFI
  firmware entries, which does the same as `sudo eac-setup boot`.

An encrypted `/boot` is not supported. The copy of the initramfs on the unencrypted EFI system partition
could contain the key of the disk, so `eac-setup` stops in this case.

## Manual setup

These are the steps that `eac-setup` runs, to do by hand or to look up what the script changes. You can switch
to the script at any point, it continues from what is already done.

:::note[Run the commands in bash]
The commands on this page are written for bash. The default shell on CachyOS is fish, which rejects some of
them, for example with `Unsupported use of '='`. Run `bash` in your terminal first, then run the commands.
:::

### If you already use Secure Boot

If you already set up Secure Boot with `sbctl`, for example with the [Secure Boot guide](/configuration/secure_boot_setup),
you don't need Setup Mode. `sbctl` can add the CachyOS EAC CA to the Secure Boot database while Secure Boot
stays enabled. It signs the change with your own Key Exchange Key (KEK), which the firmware accepts.

{/* TODO: only tested in OVMF so far, test on real hardware */}

<Steps>

1. **Check your Secure Boot setup**

    ```bash
    sudo sbctl status
    ```

    The output has to show `sbctl is installed`, `Setup Mode: Disabled` and `Secure Boot: Enabled`. If
    your keys were not created with `sbctl`, follow the setup for your boot manager from step 1 instead.

2. **Enroll the CachyOS EAC CA**

    ```bash
    sudo pacman -S cachyos-eac-signing-key
    sudo sbctl enroll-keys --append --partial db --custom --ignore-immutable
    ```

    `--append` keeps all certificates that are already enrolled, `--partial db` only changes the Secure Boot
    database (`db`) and `--ignore-immutable` lets `sbctl` write it, as Linux marks it read-only by default.

    :::caution[Run this only once]
    `sbctl` does not check which certificates are already enrolled. Every run adds the CachyOS EAC CA again,
    together with your own Database Key, and the firmware only has limited space for them.
    :::

    Check that the certificate was enrolled:

    ```bash
    sudo sbctl list-enrolled-keys
    ```

    The `db` section has to list `CachyOS EAC CA` next to your previous entries. Your own `Database Key`
    is listed twice now, which is harmless.

    If `sbctl` reports an error, the firmware did not accept the change, usually because the enrolled KEK
    is not the one in sbctl's key directory. In this case, follow the setup for your boot manager from
    step 1.

3. **Continue with the setup for your boot manager**

    Follow the [setup for your boot manager](#setup-for-your-boot-manager) from step 2. Skip step 3, the CA
    is enrolled and your boot manager is already signed. In step 6, Secure Boot is already enabled, so you
    only have to boot the EAC entry.

</Steps>

### Setup for your boot manager

<Tabs syncKey="boot-manager">
<TabItem label='Limine'>

Limine stays your default boot manager. The CachyOS-signed systemd-boot is installed next to it, in its own
directory on the EFI system partition and with its own firmware boot entry. To play, you tell the firmware to
start systemd-boot once on the next boot (`BootNext`). systemd-boot then boots the EAC kernel directly.
After that, your system starts Limine again as usual.

<Steps>

1. **Put the firmware into Setup Mode**

    If you already use Secure Boot with `sbctl`, follow [If you already use Secure Boot](#if-you-already-use-secure-boot)
    instead and continue with step 2.

    Follow [Enabling Setup Mode in UEFI](/configuration/secure_boot_setup#enabling-setup-mode-in-uefi)
    and keep Secure Boot **disabled** for now.

    ```bash
    systemctl reboot --firmware-setup
    ```

2. **Install the packages**

    If you used systemd-boot with the [Secure Boot guide](/configuration/secure_boot_setup) before switching
    to Limine, remove the self-signed systemd-boot it created first. Otherwise pacman refuses to install
    `systemd-boot-cachyos-signed`, and `sbctl` overwrites the CachyOS-signed systemd-boot:

    ```bash
    sudo sbctl remove-file /usr/lib/systemd/boot/efi/systemd-bootx64.efi
    sudo rm -f /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed
    ```

    Then install the packages:

    ```bash
    sudo pacman -S sbctl sbsigntools tpm2-tools efibootmgr cachyos-eac-signing-key linux-cachyos-eac systemd-boot-cachyos-signed
    ```

    On systems with an NVIDIA GPU, also install `linux-cachyos-eac-nvidia-open` (Turing and newer) or
    `linux-cachyos-eac-nvidia-580xx` (Maxwell, Pascal and Volta). If you use ZFS, also install
    `linux-cachyos-eac-zfs`. If you use `r8125-dkms` for a Realtek 2.5 GbE network card, also install
    `linux-cachyos-eac-r8125`.

    :::danger
    Do **not** run `bootctl install`. It would make systemd-boot your default boot manager and replace
    the fallback boot loader on the EFI system partition.
    :::

    :::caution
    Keep `ENABLE_UKI=no` (the default) in `/etc/default/limine`. With UKIs enabled, the EAC kernel is packed
    into a new image that `sbctl` signs with your own key, which EAC does not accept.
    :::

3. **Enroll the Secure Boot keys and sign Limine**

    Skip this step if you enrolled the CA as described in [If you already use Secure Boot](#if-you-already-use-secure-boot).

    `cachyos-eac-signing-key` puts the CachyOS EAC CA certificate into sbctl's directory for custom
    certificates. Enroll your own keys together with Microsoft's keys, the firmware's built-in keys and the
    CachyOS EAC CA.

    :::caution[ASUS and Gigabyte motherboards]
    On these boards, run `sudo sbctl enroll-keys --microsoft --custom` as the last command below, without
    `--firmware-builtin`. On some of them the flag creates duplicate key entries, and the board stops with a
    **Secure Boot Violation** once Secure Boot is enabled. If that already happened, delete all Secure Boot
    keys in the firmware settings to enter Setup Mode again (see
    [Enabling Setup Mode in UEFI](/configuration/secure_boot_setup#enabling-setup-mode-in-uefi)), boot
    CachyOS and run `sudo sbctl enroll-keys --microsoft --custom`. Don't use the command from the Secure Boot
    guide for this, it leaves out the CachyOS EAC CA.
    :::

    ```bash
    sudo sbctl create-keys
    sudo sbctl enroll-keys --microsoft --firmware-builtin --custom
    ```

    If `sbctl` stops with `could not enroll built-in firmware keys`, the firmware has no built-in keys and
    nothing was enrolled yet. Run the last command again without `--firmware-builtin`.

    Check that the certificate was enrolled:

    ```bash
    sudo sbctl list-enrolled-keys
    ```

    The `db` section has to list `CachyOS EAC CA`.

    Limine itself still has to be signed with your own key, so your normal boot keeps working with Secure
    Boot enabled. Follow the Limine tab in
    [Signing the Kernel Image and Boot Manager](/configuration/secure_boot_setup#signing-the-kernel-image-and-boot-manager).

    :::caution
    Never sign the EAC kernel or the CachyOS-signed systemd-boot with `sbctl`. Don't use `sbctl-batch-sign`
    or `sbctl sign` on them, even if `sbctl verify` lists them as not signed. They are signed by CachyOS.
    :::

4. **Add systemd-boot as a separate firmware boot entry**

    `sbctl` signs every file in its database again whenever a kernel or EFI binary is updated. Check that
    none of the CachyOS-signed files is in there, for example from an earlier `sbctl sign -s`:

    ```bash
    sudo sbctl list-files
    ```

    If a listed path contains `cachyos-eac` or is `/usr/lib/systemd/boot/efi/systemd-bootx64.efi`, remove it
    with `sudo sbctl remove-file <path>`. Then reinstall the packages to restore the CachyOS signatures:

    ```bash
    sudo pacman -S linux-cachyos-eac systemd-boot-cachyos-signed
    ```

    Copy the signed systemd-boot to its own directory on the EFI system partition:

    ```bash
    ESP="$(bootctl --print-esp-path)"
    sudo install -Dm644 /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed "$ESP/EFI/cachyos-eac/systemd-bootx64.efi"
    ```

    As long as `EFI/cachyos-eac` exists, `systemd-boot-cachyos-signed` updates this copy automatically.

    Then create the firmware boot entry. `--create-only` adds the entry without changing the boot order, so
    Limine stays the default:

    ```bash
    ESP_DEV="$(findmnt -no SOURCE "$ESP")"
    ESP_DISK="/dev/$(lsblk -no PKNAME "$ESP_DEV")"
    ESP_PART="$(cat "/sys/class/block/$(basename "$ESP_DEV")/partition")"
    sudo efibootmgr --create-only --disk "$ESP_DISK" --part "$ESP_PART" \
      --label "CachyOS EAC" --loader '\EFI\cachyos-eac\systemd-bootx64.efi'
    ```

    Check that the new entry is listed and that `BootOrder` still starts with Limine:

    ```bash
    efibootmgr
    ```

5. **Create the EAC boot entry**

    systemd-boot reads its configuration from the EFI system partition. The Limine hook keeps the EAC
    kernel and its initramfs up to date in a directory named after your machine ID. Check that both exist:

    ```bash
    ESP="$(bootctl --print-esp-path)"
    KERNEL="/$(cat /etc/machine-id)/linux-cachyos-eac/vmlinuz"
    INITRD="/$(cat /etc/machine-id)/linux-cachyos-eac/initramfs"
    sudo ls -l "$ESP$KERNEL" "$ESP$INITRD"
    ```

    Then build the kernel command line from your running system plus the EAC options:

    ```bash
    EAC_REQ="lockdown=integrity lsm=landlock,lockdown,yama,integrity,bpf iommu.passthrough=0 intel_iommu=on module.sig_enforce=1 sysctl.kernel.kexec_load_disabled=1"
    EAC_OPTS="$(sed -E 's/(^| )(BOOT_IMAGE|initrd)=[^ ]*//g' /proc/cmdline) $EAC_REQ"
    echo "$EAC_OPTS"
    ```

    The output has to contain your `root=` option and end with the EAC options. Write the entry and make
    it the default, so systemd-boot starts it without showing a menu. This replaces an existing
    `loader/loader.conf`, which is fine here, because systemd-boot only starts the EAC entry:

    ```bash
    printf 'title   CachyOS (EAC)\nlinux   %s\ninitrd  %s\noptions %s\n' "$KERNEL" "$INITRD" "$EAC_OPTS" \
      | sudo install -Dm644 /dev/stdin "$ESP/loader/entries/cachyos-eac.conf"
    printf 'default cachyos-eac.conf\ntimeout 0\n' | sudo install -Dm644 /dev/stdin "$ESP/loader/loader.conf"
    ```

    To see the systemd-boot menu anyway, hold <kbd>Space</kbd> while it starts.

    :::caution
    The Limine menu also shows an entry for `linux-cachyos-eac`. Booting it through Limine does **not**
    pass the EAC checks. Always use the "CachyOS EAC" firmware entry.
    :::

    {/* TODO: hide the linux-cachyos-eac entry in Limine (limine-entry-tool has no per-kernel exclude yet) */}

6. **Enable Secure Boot and boot into EAC**

    If Secure Boot is already enabled, skip to booting into EAC.

    Reboot into the firmware settings and enable Secure Boot. See the ASUS notes in the
    [Secure Boot guide](/configuration/secure_boot_setup#signing-the-kernel-image-and-boot-manager) if your board has no
    Secure Boot switch.

    ```bash
    systemctl reboot --firmware-setup
    ```

    To boot into EAC, set the "CachyOS EAC" entry as `BootNext` and reboot. `sudo eac-setup boot` does the
    same:

    ```bash
    EAC_BOOTNUM="$(efibootmgr | sed -n 's/^Boot\([0-9A-F]\{4\}\)\* CachyOS EAC.*/\1/p')"
    sudo efibootmgr --bootnext "$EAC_BOOTNUM" && systemctl reboot
    ```

    `BootNext` only applies to the next boot. The reboot after your gaming session starts Limine again.

</Steps>

    Microsoft's keys, the firmware's built-in keys and the CachyOS EAC CA.

    :::caution[ASUS and Gigabyte motherboards]

    `--firmware-builtin`. On some of them the flag creates duplicate key entries, and the board stops with a
    **Secure Boot Violation** once Secure Boot is enabled. If that already happened, delete all Secure Boot
    keys in the firmware settings to enter Setup Mode again (see
    [Enabling Setup Mode in UEFI](/configuration/secure_boot_setup#enabling-setup-mode-in-uefi)), boot
    CachyOS and run `sudo sbctl enroll-keys --microsoft --custom`. Don't use the command from the Secure Boot
    guide for this, it leaves out the CachyOS EAC CA.
    :::

    ```bash
    sudo sbctl create-keys
    sudo sbctl enroll-keys --microsoft --firmware-builtin --custom
    ```

    If `sbctl` stops with `could not enroll built-in firmware keys`, the firmware has no built-in keys and
    nothing was enrolled yet. Run the last command again without `--firmware-builtin`.

    Check that the certificate was enrolled:

    ```bash
    sudo sbctl list-enrolled-keys
    ```

    The `db` section has to list `CachyOS EAC CA`.

    Then sign your normal kernels, otherwise they won't boot once Secure Boot is enabled. The command skips
    the EAC kernel, which is already signed by CachyOS:

    ```bash
    sudo find /boot -maxdepth 1 -name 'vmlinuz-*' ! -name vmlinuz-linux-cachyos-eac -exec sbctl sign -s {} \;
    sudo sbctl list-files
    ```

    The output has to show each of your normal kernels as signed.

4. **Keep sbctl away from the CachyOS-signed files**

    The EAC kernel and systemd-boot are already signed by CachyOS. If `sbctl` signs them again with your
    own key, EAC no longer recognizes them. `cachyos-eac-signing-key` stops sbctl's initramfs hook from
    signing the EAC kernel, but `sbctl` still signs every file in its database, for example after running
    `sbctl-batch-sign` or `sbctl sign -s`.

    ```bash
    sudo sbctl list-files
    ```

    If `vmlinuz-linux-cachyos-eac`, `systemd-bootx64.efi` or `BOOTX64.EFI` are listed, remove them and
    reinstall the packages to restore the CachyOS signatures:

    ```bash
    sudo sbctl remove-file /boot/vmlinuz-linux-cachyos-eac
    sudo sbctl remove-file /boot/EFI/systemd/systemd-bootx64.efi
    sudo sbctl remove-file /boot/EFI/BOOT/BOOTX64.EFI
    sudo sbctl remove-file /usr/lib/systemd/boot/efi/systemd-bootx64.efi
    sudo pacman -S linux-cachyos-eac systemd-boot-cachyos-signed
    sudo bootctl install
    ```

    For files that aren't listed, `sbctl` reports `doesn't exist in database`, which is fine.

    Check the signatures. Each file has to show exactly **one** signature, issued by `CachyOS EAC CA`,
    followed by `Signature verification OK`:

    ```bash
    for f in /boot/vmlinuz-linux-cachyos-eac /boot/EFI/systemd/systemd-bootx64.efi; do
      sudo sbverify --list "$f"
      sudo sbverify --cert /usr/share/cachyos-eac/cachyos-eac-ca.crt "$f"
    done
    ```

    `sbctl verify` keeps listing these files as not signed, because it only counts signatures made with your
    own key. Don't sign them. `sbctl-batch-sign` skips them.

5. **Create the EAC boot entry**

    EAC checks the kernel command line for the required options, so the EAC kernel needs its own boot
    entry. The entry that `sdboot-manage` creates automatically ("Linux CachyOS Eac") lacks these options
    and is overwritten on updates, so create a separate entry based on the command line of your running
    system:

    {/* TODO: replace with automatic entry generation (sdboot-manage or package hook) */}

    ```bash
    EAC_REQ="lockdown=integrity lsm=landlock,lockdown,yama,integrity,bpf iommu.passthrough=0 intel_iommu=on module.sig_enforce=1 sysctl.kernel.kexec_load_disabled=1"
    EAC_OPTS="$(sed -E 's/(^| )(BOOT_IMAGE|initrd)=[^ ]*//g' /proc/cmdline) $EAC_REQ"
    echo "$EAC_OPTS"
    ```

    The output has to contain your `root=` option and end with the EAC options. Then write the entry:

    ```bash
    printf 'title   CachyOS (EAC)\nlinux   /vmlinuz-linux-cachyos-eac\ninitrd  /initramfs-linux-cachyos-eac.img\noptions %s\n' "$EAC_OPTS" \
      | sudo install -Dm644 /dev/stdin /boot/loader/entries/cachyos-eac.conf
    ```

    :::caution
    Don't remove any of the EAC options from this entry. Without them, EAC refuses to start the game.
    :::

6. **Enable Secure Boot and boot the EAC entry**

    If Secure Boot is already enabled, skip to booting the EAC entry.

    Reboot into the firmware settings and enable Secure Boot. See the ASUS notes in the
    [Secure Boot guide](/configuration/secure_boot_setup#signing-the-kernel-image-and-boot-manager) if your board has no
    Secure Boot switch.

    ```bash
    systemctl reboot --firmware-setup
    ```

    To boot the EAC entry, select **CachyOS (EAC)** in the systemd-boot menu, or run:

    ```bash
    systemctl reboot --boot-loader-entry=cachyos-eac.conf
    ```

</Steps>

</TabItem>
<TabItem label='rEFInd'>

rEFInd stays your default boot manager. As with Limine, the CachyOS-signed systemd-boot is installed in its own
directory on the EFI system partition and gets its own firmware boot entry. To play, you tell the firmware to
start systemd-boot once on the next boot (`BootNext`). systemd-boot then boots the EAC kernel directly. After
that, your system starts rEFInd again as usual.

These steps need the EFI system partition mounted at `/boot`, which is how the CachyOS installer sets up
rEFInd. Check it:

```bash
bootctl --print-esp-path
```

The output has to be `/boot`. Other layouts, for example an EFI system partition at `/boot/efi` from older
installations, are not supported.

<Steps>

1. **Put the firmware into Setup Mode**

    If you already use Secure Boot with `sbctl`, follow [If you already use Secure Boot](#if-you-already-use-secure-boot)
    instead and continue with step 2.

    Follow [Enabling Setup Mode in UEFI](/configuration/secure_boot_setup#enabling-setup-mode-in-uefi)
    and keep Secure Boot **disabled** for now.

    ```bash
    systemctl reboot --firmware-setup
    ```

2. **Install the packages**

    If you used systemd-boot with the [Secure Boot guide](/configuration/secure_boot_setup) before switching
    to rEFInd, remove the self-signed systemd-boot it created first. Otherwise pacman refuses to install
    `systemd-boot-cachyos-signed`, and `sbctl` overwrites the CachyOS-signed systemd-boot:

    ```bash
    sudo sbctl remove-file /usr/lib/systemd/boot/efi/systemd-bootx64.efi
    sudo rm -f /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed
    ```

    Then install the packages:

    ```bash
    sudo pacman -S sbctl sbsigntools tpm2-tools efibootmgr cachyos-eac-signing-key linux-cachyos-eac systemd-boot-cachyos-signed
    ```

    On systems with an NVIDIA GPU, also install `linux-cachyos-eac-nvidia-open` (Turing and newer) or
    `linux-cachyos-eac-nvidia-580xx` (Maxwell, Pascal and Volta). If you use ZFS, also install
    `linux-cachyos-eac-zfs`. If you use `r8125-dkms` for a Realtek 2.5 GbE network card, also install
    `linux-cachyos-eac-r8125`.

    :::danger
    Do **not** run `bootctl install`. It would make systemd-boot your default boot manager and replace
    the fallback boot loader on the EFI system partition.
    :::

3. **Enroll the Secure Boot keys and sign rEFInd**

    Skip this step if you enrolled the CA as described in [If you already use Secure Boot](#if-you-already-use-secure-boot).

    `cachyos-eac-signing-key` puts the CachyOS EAC CA certificate into sbctl's directory for custom
    certificates. Enroll your own keys together with Microsoft's keys, the firmware's built-in keys and the
    CachyOS EAC CA.

    :::caution[ASUS and Gigabyte motherboards]
    On these boards, run `sudo sbctl enroll-keys --microsoft --custom` as the last command below, without
    `--firmware-builtin`. On some of them the flag creates duplicate key entries, and the board stops with a
    **Secure Boot Violation** once Secure Boot is enabled. If that already happened, delete all Secure Boot
    keys in the firmware settings to enter Setup Mode again (see
    [Enabling Setup Mode in UEFI](/configuration/secure_boot_setup#enabling-setup-mode-in-uefi)), boot
    CachyOS and run `sudo sbctl enroll-keys --microsoft --custom`. Don't use the command from the Secure Boot
    guide for this, it leaves out the CachyOS EAC CA.
    :::

    ```bash
    sudo sbctl create-keys
    sudo sbctl enroll-keys --microsoft --firmware-builtin --custom
    ```

    If `sbctl` stops with `could not enroll built-in firmware keys`, the firmware has no built-in keys and
    nothing was enrolled yet. Run the last command again without `--firmware-builtin`.

    Check that the certificate was enrolled:

    ```bash
    sudo sbctl list-enrolled-keys
    ```

    The `db` section has to list `CachyOS EAC CA`.

    rEFInd and your normal kernels still have to be signed with your own key, so your normal boot keeps
    working with Secure Boot enabled. The `find` command skips the EAC kernel, which is already signed by
    CachyOS:

    ```bash
    sudo sbctl sign -s /boot/EFI/refind/refind_x64.efi
    sudo find /boot -maxdepth 1 -name 'vmlinuz-*' ! -name vmlinuz-linux-cachyos-eac -exec sbctl sign -s {} \;
    sudo sbctl list-files
    ```

    The output has to show rEFInd and each of your normal kernels as signed. `sbctl` signs them again
    after kernel updates. pacman doesn't update rEFInd on the EFI system partition. If you run
    `refind-install` yourself, run `sudo sbctl sign-all` afterwards.

    :::caution
    Never sign the EAC kernel or the CachyOS-signed systemd-boot with `sbctl`. Don't use `sbctl-batch-sign`
    or `sbctl sign` on them, even if `sbctl verify` lists them as not signed. They are signed by CachyOS.
    :::

4. **Add systemd-boot as a separate firmware boot entry**

    `sbctl` signs every file in its database again whenever a kernel or EFI binary is updated. Check that
    none of the CachyOS-signed files is in there, for example from an earlier `sbctl sign -s`:

    ```bash
    sudo sbctl list-files
    ```

    If a listed path contains `cachyos-eac` or is `/usr/lib/systemd/boot/efi/systemd-bootx64.efi`, remove it
    with `sudo sbctl remove-file <path>`. Then reinstall the packages to restore the CachyOS signatures:

    ```bash
    sudo pacman -S linux-cachyos-eac systemd-boot-cachyos-signed
    ```

    Copy the signed systemd-boot to its own directory on the EFI system partition:

    ```bash
    ESP="$(bootctl --print-esp-path)"
    sudo install -Dm644 /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed "$ESP/EFI/cachyos-eac/systemd-bootx64.efi"
    ```

    As long as `EFI/cachyos-eac` exists, `systemd-boot-cachyos-signed` updates this copy automatically.

    Then create the firmware boot entry. `--create-only` adds the entry without changing the boot order, so
    rEFInd stays the default:

    ```bash
    ESP_DEV="$(findmnt -no SOURCE "$ESP")"
    ESP_DISK="/dev/$(lsblk -no PKNAME "$ESP_DEV")"
    ESP_PART="$(cat "/sys/class/block/$(basename "$ESP_DEV")/partition")"
    sudo efibootmgr --create-only --disk "$ESP_DISK" --part "$ESP_PART" \
      --label "CachyOS EAC" --loader '\EFI\cachyos-eac\systemd-bootx64.efi'
    ```

    Check that the new entry is listed and that `BootOrder` still starts with rEFInd:

    ```bash
    efibootmgr
    ```

5. **Create the EAC boot entry**

    systemd-boot reads its configuration from the EFI system partition, where the EAC kernel and its
    initramfs already are. Build the kernel command line from your running system plus the EAC options:

    ```bash
    EAC_REQ="lockdown=integrity lsm=landlock,lockdown,yama,integrity,bpf iommu.passthrough=0 intel_iommu=on module.sig_enforce=1 sysctl.kernel.kexec_load_disabled=1"
    EAC_OPTS="$(sed -E 's/(^| )(BOOT_IMAGE|initrd)=[^ ]*//g' /proc/cmdline) $EAC_REQ"
    echo "$EAC_OPTS"
    ```

    The output has to contain your `root=` option and end with the EAC options. Write the entry and make
    it the default, so systemd-boot starts it without showing a menu:

    ```bash
    ESP="$(bootctl --print-esp-path)"
    printf 'title   CachyOS (EAC)\nlinux   /vmlinuz-linux-cachyos-eac\ninitrd  /initramfs-linux-cachyos-eac.img\noptions %s\n' "$EAC_OPTS" \
      | sudo install -Dm644 /dev/stdin "$ESP/loader/entries/cachyos-eac.conf"
    printf 'default cachyos-eac.conf\ntimeout 0\n' | sudo install -Dm644 /dev/stdin "$ESP/loader/loader.conf"
    ```

    To see the systemd-boot menu anyway, hold <kbd>Space</kbd> while it starts.

    rEFInd finds the EAC kernel and systemd-boot on its own and adds them to its menu. Anything started from
    the rEFInd menu does **not** pass the EAC checks, because rEFInd is signed with your own key. Hide both
    entries:

    ```bash
    printf '\n# Easy Anti-Cheat: boot these only through the "CachyOS EAC" firmware entry\ndont_scan_files +,vmlinuz-linux-cachyos-eac\ndont_scan_dirs +,EFI/cachyos-eac\n' \
      | sudo tee -a "$ESP/EFI/refind/refind.conf" >/dev/null
    ```

    The `+` keeps the files and directories that rEFInd already skips. From the next boot on, the rEFInd
    menu only shows your normal kernels.

6. **Enable Secure Boot and boot into EAC**

    If Secure Boot is already enabled, skip to booting into EAC.

    Reboot into the firmware settings and enable Secure Boot. See the ASUS notes in the
    [Secure Boot guide](/configuration/secure_boot_setup#signing-the-kernel-image-and-boot-manager) if your board has no
    Secure Boot switch.

    ```bash
    systemctl reboot --firmware-setup
    ```

    To boot into EAC, set the "CachyOS EAC" entry as `BootNext` and reboot. `sudo eac-setup boot` does the
    same:

    ```bash
    EAC_BOOTNUM="$(efibootmgr | sed -n 's/^Boot\([0-9A-F]\{4\}\)\* CachyOS EAC.*/\1/p')"
    sudo efibootmgr --bootnext "$EAC_BOOTNUM" && systemctl reboot
    ```

    `BootNext` only applies to the next boot. The reboot after your gaming session starts rEFInd again.

</Steps>

## Verifying the setup

After booting the EAC entry, run `eac-status` from `cachyos-settings`:

```bash
sudo eac-status
```

It checks Secure Boot and Setup Mode, the TPM, the enrolled CachyOS EAC CA, the signatures of the EAC
kernel and systemd-boot, the kernel command line, lockdown, module signatures, kexec, the IOMMU and which
certificates the firmware used to verify the boot (from the TPM event log). Every check has to show
`[ OK ]`, and the last line has to read `All checks passed`. In your normal boot entry, it only checks the
firmware and the boot files, and ends with `The boot files are ready` if they are.

These checks only cover your system. Whether a game starts is still up to Easy Anti-Cheat and the game.

A Microsoft certificate in the TPM event log is fine (used for GPU firmware) and is not reported. Any other
certificate, such as your own "Database Key", is reported with `[WARN] Boot was also verified by`.

## Troubleshooting

### `eac-status` reports two signatures or your own key

`has 2 signatures` or `Boot was also verified by Database Key` means that `sbctl` signed the EAC kernel or
systemd-boot again with your own key. Versions of `cachyos-eac-signing-key` before 1-2 let sbctl's initramfs hook
do this whenever the initramfs was rebuilt, so update your system first:

```bash
sudo pacman -Syu
```

Then run `sudo eac-setup` again. It removes the files from sbctl's database and restores the CachyOS
signatures. To do this by hand, follow the steps below.

With systemd-boot, repeat step 4 of the systemd-boot tab in
[Setup for your boot manager](#setup-for-your-boot-manager) to remove the files from sbctl's database and
reinstall the packages.

With Limine or rEFInd, do **not** follow that step. Its `bootctl install` would make systemd-boot your
default boot manager and replace the fallback boot loader on the EFI system partition. Check sbctl's database
instead:

```bash
sudo sbctl list-files
```

If a listed path contains `cachyos-eac`, or is `/usr/lib/systemd/boot/efi/systemd-bootx64.efi` (left over
from the systemd-boot steps of the Secure Boot guide), remove it with `sudo sbctl remove-file <path>`. Then
reinstall the packages and copy the signed systemd-boot again:

```bash
sudo pacman -S linux-cachyos-eac systemd-boot-cachyos-signed
ESP="$(bootctl --print-esp-path)"
sudo install -Dm644 /usr/lib/systemd/boot/efi/systemd-bootx64.efi.signed "$ESP/EFI/cachyos-eac/systemd-bootx64.efi"
```

### `eac-status` reports that the boot was not verified by the CachyOS EAC CA

If `Boot was not verified by CachyOS EAC CA` comes together with failed kernel command line checks, the
wrong entry was booted. See [The game says the system is not supported](#the-game-says-the-system-is-not-supported).

If it is the only failed check, the firmware did not record which certificate it used to verify the boot
files. On MSI boards, the most likely cause is the default Secure Boot policy: the firmware starts every
boot file without verifying it, even with Secure Boot enabled.

Open the Secure Boot page of the firmware setup. Depending on the board, it is under
**Settings > Advanced > Windows OS Configuration > Secure Boot** or **Settings > Security > Secure Boot**.
The name of the option depends on the firmware version:

| Option                 | Value                                                        |
| ---------------------- | ------------------------------------------------------------ |
| Image Execution Policy | **Deny Execute** for **Fixed Media** and **Removable Media** |
| Secure Boot Preset     | **Maximum Security**                                         |
| Target OS              | **Windows UEFI OS**                                          |

:::caution
Don't switch **Secure Boot Mode** to **Standard** and don't restore the factory keys. Both remove the
CachyOS EAC CA and your own keys.
:::

Save the change, boot the EAC entry and run `sudo eac-status` again. If it now reports that the
CachyOS EAC CA is not enrolled, the firmware reset its keys. Run `sudo eac-setup` again.

### The game says the system is not supported

Run `sudo eac-status` in the EAC entry and fix every check marked `[FAIL]`. Most often the wrong entry was
booted, and `eac-status` reports the EAC options as missing from the kernel command line. Reboot with
`sudo eac-setup boot`. In systemd-boot, you can also select **CachyOS (EAC)**, not the automatically created
"Linux CachyOS Eac" entry. With Limine, rEFInd or GRUB, don't start the EAC kernel from the menu of your boot
manager.

### Limine or rEFInd starts instead of the EAC entry

Check that `BootNext` was set before rebooting:

```bash
efibootmgr | grep -E 'BootNext|CachyOS EAC'
```

If the "CachyOS EAC" entry is missing, the firmware removed it, which some boards do after a firmware
update or reset. Run `sudo eac-setup` to create it again, or repeat step 4 of the Limine or rEFInd tab in
[Setup for your boot manager](#setup-for-your-boot-manager). You can also pick "CachyOS EAC" in the
firmware's one-time boot menu.

### A module does not load in the EAC entry

Modules built with DKMS are not signed with the kernel's key and cannot be loaded. Use the modules
shipped for the EAC kernel (`linux-cachyos-eac-nvidia-open`, `linux-cachyos-eac-nvidia-580xx`,
`linux-cachyos-eac-zfs` or `linux-cachyos-eac-r8125`), or boot your normal kernel for anything that needs
DKMS modules.
